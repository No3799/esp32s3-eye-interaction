## 二、第 2 周：让网页能反过来指挥设备

第 1 周的链路是**单向**的：板子推数据，网页看数据。网页刷新再多次也只能看到已有记录 ——
**没有任何办法让设备再采一次**。

第 2 周补上反方向的通道，并把它做成一条可核查的证据链：

```
网页点「重新采集」
   │  POST /api/command
   ▼
① issued      服务器受理，生成 request_id 并入队
   │  板子下次上报（≤1s）时，指令随 /api/data 的**响应体**捎带下发
   ▼
② delivered   指令已到达板子
   │  板子回报 cmd_state="received"
   ▼
③ received    设备确认接收，开始按参数采集
   │  板子采完最后一条，回报 cmd_state="done"
   ▼
④ done        执行结果：设备回报执行完毕，新数据已入库（可按 request_id 精确回溯）
   └─ 设备回报"我试了没干成" → failed，并带上原因
   └─ 任一步没人回应      → timeout，并记录卡在哪一段（accept / exec）
```

**三种结局必须分开看**，因为它们要查的地方完全不同：

| 结局 | 谁知道结果 | 该去查什么 |
|---|---|---|
| `done` | 设备 | — （新数据在库里，`sample_count` 是带该 `request_id` 的记录条数） |
| `failed` | **设备** | 设备/传感器的执行端（原因在 `note` 里） |
| `timeout` | **没人知道** | 网络、供电、设备是否掉线（`timeout_stage` 区分"没来取"/"没执行完"） |

**数据层如何区分「新采集」与「历史记录」**（不靠时间窗口猜）：

| 字段 | 定时上报 | 指令触发 |
|---|---|---|
| `trigger` | `'timer'` | `'command'` |
| `request_id` | `NULL` | 该次指令的 id |

指令**不推送给设备**，而是搭车在板子自己的上报响应里 —— 板子不需要开监听端口，
也不用引入 MQTT/WebSocket，改动最小。代价是指令送达最多延迟 1 秒（等下一次上报），
对本场景完全够用；若将来要做秒级以下的实时控制，才值得换成长连接。

**同一台设备的同类指令，同一时刻只允许一条在途**（重复点击返回 409）——
否则连点 5 次会排队 5 条，最后一条几十秒后才执行，页面上呈现成「完成 / 超时」混杂。

设计细节见 [`docs/design/08-下行指令与回执状态机.md`](docs/design/08-下行指令与回执状态机.md)
与**首版状态图** [`docs/design/10-指令状态机与状态图.md`](docs/design/10-指令状态机与状态图.md)，
真机验收证据见 [`week1/第2周验收记录.md`](week1/第2周验收记录.md)（其中第七节是按任务卡逐条补齐的记录）。

## 三、第 3 周：按键发起求助，以及三级反馈

前两周的交互**都发生在远端**：板子按时上报，网页能反过来指挥设备。但站在设备旁边的
那个人没有办法和它交互 —— 他只能等，或者掏出手机打开网页。

第 3 周补上这一半：**直接按板子上的键**就能在本地和远端同时得到反馈。
按键的语义不是"再采一批数据"，而是**发起一条教学求助测试消息** ——
数据只是这条消息的上下文。

```
按下实体键（MENU / PLAY / UP+ / DN-）
   ├─► 绿灯短亮 60 ms              ← ① 本地确认：按到了。**这一步不经过网络**
   ├─► 板子 POST /api/help        ← 一条求助消息（带 2 条环境快照作上下文）
   │      ├─ 送出去了 ─► 连闪 2 次  ← ② VPS 接收成立
   │      └─ 没送出去 ─► 快闪 5 次  ← 如实告知失败（绝不假装成功）
   ├─► 远端有人点「我来处理」      ← ③ 查看者回应：真人 + 时间戳
   │      └─► 回传指令搭车下发 ─► 慢闪 4 次   ← 把"有人理你了"带回设备
   └─► 远端有人点「取消求助」      └─► 长亮 1 秒
```

**三级反馈是三件不同的事，界面绝不合并成一句"状态"**：
① 本地确认发生在设备上（断网也有效）；② VPS 接收的证据是服务器时间戳；
③ 查看者回应必须有真人点过按钮。**没有第 ③ 级的证据时，页面不会显示"对方已收到"。**

这句不是自觉，是结构决定的：界面上 ③ 徽标的唯一来源就是 `ack_ms`，没有别的判断路径。

### 硬件事实（查过原理图与官方文档，不是猜的）

| 项目 | 事实 | 出处 |
|---|---|---|
| 4 个用户按键 | 挂在**同一条 ADC**（`ADC1_CH0` = GPIO1）上的电阻梯，靠电压区分 | 原理图第 4 页 |
| 各键电压 | UP+ 380 / DN− 820 / PLAY 1980 / MENU 2410 mV | 原理图（实测偏差 ≤20 mV） |
| 本地反馈 | 只有一颗绿灯（GPIO3），且**必须开漏驱动、不得上拉** | 官方用户指南 |
| 蜂鸣器 / RGB 灯 | **都没有** | 原理图 + 官方 BSP 能力表 |

### 三种触发方式在数据层分得开

| 触发方式 | `trigger` | `request_id` | `button` |
|---|---|---|---|
| 定时上报 | `timer` | `NULL` | `NULL` |
| 网页下发指令 | `command` | `CMD-20260920-0002` | `NULL` |
| **板载实体按键** | `button` | `BTN-2a3613-MENU-0003` | `MENU` |

**真机实测①（2026-09-20，按键语义改造**之前**的版本）** —— 四个键各按一次，
每次恰好新采 5 条，用来验证按键判读与事件 id 聚合：

| 事件 id | 按键 | 记录 id | 入库跨度 | 按下→首条采样 |
|---|---|---|---|---|
| `BTN-2a3613-UP+-0001` | UP+ | 26153 ~ 26157 | 1608 ms | 471 ms |
| `BTN-2a3613-DN--0002` | DN− | 26160 ~ 26164 | 1115 ms | 1221 ms |
| `BTN-2a3613-MENU-0003` | MENU | 26167 ~ 26171 | 968 ms | 1061 ms |
| `BTN-2a3613-PLAY-0004` | PLAY | 26175 ~ 26179 | 893 ms | 691 ms |

> 这一批是**改造前**的行为，保留在此是因为它记录了一个真实的判断：
> 一次按键采 5 条太慢了（实测一次 HTTP 往返要 0.5~2.5 秒，5 条意味着站在板子旁边的人
> 要等好几秒），与"按下就该立刻有反馈"直接冲突。
> 改造后改为 **1 条求助消息 + 2 条上下文采样**，采样失败不影响求助成败。

**真机实测②（2026-09-23 改造后）** —— 三个键各按一次，每次 1 条求助事件 + 2 条上下文采样；
三级反馈逐级点亮，回应/取消都生成了回传指令且板子确认执行（2574~3287 ms）。
完整记录见 [`week1/第3周验收记录.md`](week1/第3周验收记录.md)。

**断网实测（2026-09-28）** —— 停掉服务器、确认静默真正开始之后按一下键：
绿灯**短亮**（本地确认成立）+ **快闪 5 次**（如实告知没送出去）；
该窗口内服务器侧求助事件 **0 条**，恢复后也**没有补发**一条迟到的记录。
见验收记录第十节。

### 这一周也修掉了一个会产出"错误证据"的 bug

事件 id 原先是内存里的计数器，**板子一重启就归零**，于是两次不同时间按的 UP+
生成了同一个 id，被服务器按 id 聚合时**误合并成一条**（样本数 10、跨度 105 秒）。
它产出的不是"没有数据"，而是看起来像证据、实际是错的数字 —— **错的证据比没有证据更危险**。
修复方式是给事件 id 加**上电随机前缀**（`BTN-2a3613-…`），并在网页上把跨度异常的事件
直接标红提示。完整过程见 [`docs/design/09`](docs/design/09-实体按键与本地反馈.md) 第 3 节。

设计细节见 [`docs/design/09-实体按键与本地反馈.md`](docs/design/09-实体按键与本地反馈.md)，
真机证据见 [`week1/第3周验收记录.md`](week1/第3周验收记录.md)。

## 四、第 4 周：一句话查数据，或者让设备再采一次

前两周已经有两条路：**读历史**（第 1 周）和 **下指令**（第 2 周）。
这一周要解决的是"用一句人话选中其中一条，并且不许说错"。

难点不在接模型，而在**概率性的语言输出怎么落到确定性的任务执行上**。

### 三个角色，权限差别极大

| | ① 开发助手 | ② 产品运行时模型 | ③ 受限工具 |
|---|---|---|---|
| 是谁 | 写这份代码的 AI（IDE 里的助手） | 本地 Ollama 的 `qwen3.8-q2` | `read_latest` / `request_recollect` |
| 能看到 | 整个磁盘、终端、代码、数据库 | **只有**用户那一句话 | 数据库连接、指令状态机 |
| 能做什么 | 改代码、跑命令、装环境 | 只输出一个 JSON：意图 + 参数 | 读一条记录 / 下发一条指令 |
| 出错后果 | 代码错，改回来 | 判错意图 | 下错指令，**会动硬件** |

**模型只出参数，不出结论。** 回答里的每一个数字、时间、状态，都是服务端
从工具返回值里取的 —— 模型不参与写答案。

### 两种任务怎么落到已验证的接口上

| 用户的话 | 意图 | 工具 | 复用的接口 | 产生新数据？ |
|---|---|---|---|---|
| 查看上次数据 | `query_latest` | `read_latest` | 第 1 周的 readings 查询 | **否** |
| 重新采集一次 | `request_recollect` | `request_recollect` | 第 2 周的 `CommandStore` | **是** |

底层通信**一行没改**，固件也没改。第 4 周只是在已有两条路上各加了一个入口。

### 没有完成证据，就不许说"已采集成功"

这是本周的硬要求，做了三层独立防线：

1. **模板由服务端拼装** —— 状态是 `timeout` 就写"超时"，是 `failed` 就写"失败"。
   判"完成"要求**两项同时成立**：设备回执 `done` **且** 库里有带同一 `request_id` 的新记录。
   只有回执没记录不算（回执可能是迟到的旧报文），只有记录没回执也不算。
2. **断言闸门** —— 独立扫描文本里的"已采集成功""采集成功"等说法，无证据时判不合格。
3. **打包前二次保险** —— 与闸门独立再查一遍，防止"改了一处漏了另一处"。

为什么不让模型润色措辞：它会顺手把"12 条"写成"10 条"。可选的润色模式必须过两关 ——
过断言闸门，**且数字集合不能变**，变了就回退模板。

### "不能生成坐标"在这台板子上怎么落

任务卡要求「无位置或过期位置须说明不足，不能生成坐标」。这台板子上**没有定位传感器**
（只有加速度计、摄像头、一颗 LED、四个按键），所以：

- **无位置** → 问坐标/经纬度/在哪，明确说"没有定位数据源"，**不生成坐标**
- **过期位置** → 读到的数据超过 `STALE_SECONDS`，在回答里标「⚠️ 这条数据已过期」

验收时用正则找坐标数字对判"有没有编坐标"，并用正常读数 `X=-0.0083` 做**反例**，
确认探测器不会把普通读数误判成坐标。

### 实测（真板子 + 真模型 + 真浏览器）

四类测试 7 个用例全过：

| 用例 | 关键实测 |
|---|---|
| 查看上次数据 | 采集记录数 315→315（**未新增**）；回答含时间 `10:05:23` 与来源 |
| 重新采集一次 | `CMD-20261023-0010`，`status=done`，12 条新记录，采集记录数 315→327 |
| 同一旧数据：查看 vs 重采 | 查看 `10:06:38` / 重采最后一条 `10:06:45`（**后者确实更新**） |
| 含糊「看看数据吧」 | `intent=unclear`，`tool=None`，未执行，列出两个选项 |
| 越界「给个坐标」 | `intent=unsupported`，明确说没有定位源，**无坐标** |
| 离线设备点名采集 | `error=device_offline`，未下发 |
| 不存在的设备 `device999` | `error=device_not_allowed`，未执行 |

"无证据不许说成功"专项：真服务器对离线设备下发 `CMD-20261023-0013`，
**30.5 秒** 后由服务器侧主动判超时（`timeout_stage=accept`）并落库；
对 timeout / failed / issued 三种无证据状态逐一检查，**零成功声明**。

真实浏览器 18 项全过。刻意用**真鼠标事件**（`Input.dispatchMouseEvent`）而不是
JS 的 `.click()` —— 后者对隐藏元素照样生效，"按钮其实点不到"会被测成通过。

界面上除了回答正文，还显示一行元信息：
`意图 query_latest | 工具 read_latest | 3.03 秒 | 设备 team01-esp32s3eye`。
**这一行是"受限"的可见证据** —— 看得出它调了哪个工具、有没有真查到东西。

## 七、系统架构

```
┌──────────────────────────┐         ┌──────────────────────────┐        ┌─────────────────┐
│   ESP32-S3-EYE           │  WiFi   │   服务器 (server.py)      │  HTTP  │   网页           │
│                          │ 2.4GHz  │   0.0.0.0:8000           │        │  index.html     │
│  QMA6100P ──I2C──┐       │ ──────► │                          │ ◄─────►│  实时数值卡片    │
│                 ├─► app  │  POST   │  /api/data   接收存储     │ GET/   │  趋势曲线        │
│  OV2640 ──DVP───┤  main  │ /api/data│ /api/latest  最新+年龄    │ POST   │  摄像头画面      │
│  4键 ADC ─GPIO1─┤       │         │ /api/history 历史         │        │  CSV 下载        │
│  绿灯   ◄─GPIO3─┘       │ ◄───────┤ /api/buttons 实体按键事件  │        │  主动交互面板    │
│                          │ 捎带指令 │ /api/command 下发指令     │        │  教学求助面板    │
│  上行 1Hz + 按键突发      │         │ /api/export.csv /devices  │        │  未更新提示      │
│                          │  :81    │ /api/camera   MJPEG 中继  │        │                 │
│  MJPEG 流服务 ◄──────────┼─────────┤  (camera_relay.py)       │        │                 │
└──────────────────────────┘  拉 1 路  └───────────┬──────────────┘        └─────────────────┘
                                                   │
                                            SQLite readings.db
```

设计要点：

- **板子只推 1 路数据**，摄像头流由服务器作为「唯一客户端」拉取后分发给任意多个浏览器 —— 板端连接数恒定，多人同时观看不崩。
- **权威时间是服务端的 `server_ms`**，板子无 RTC，`device_ms` 只能用于测间隔。
- **每条记录带 `src_ip`**，这是「数据来自真实设备而非页面常量」的证据。
- **数据自带「谁触发的」**：`trigger` 三态（`timer`/`command`/`button`）+ `request_id` + `button`，
  所以"这批数据是这次动作新采的"是**数据库里的直接关联**，不是靠时间窗口猜。
- **只有一条下行通道**：板子不监听端口，待执行指令搭在 `/api/data` 的**响应体**里捎带下发，不引入 MQTT/WebSocket。
- 服务端**零第三方依赖**，只用 Python 标准库，换台电脑拷过去就能跑。

## 十、验收演练（老师要看的）

### 基本链路（第 1 周）

1. 打开页面 → 数值实时刷新，板子静置时 |a| ≈ 1.00 g
2. 拿起开发板晃动/翻转 → 数值与曲线同步变化
3. **拔掉板子 USB 供电** → 数值冻结、时间停在最后一刻
4. 等 5 秒 → 页面提示「未更新 · 已 N 秒」

第 3~4 步是核心：证明页面数值不是写死的，而是真的来自一台会停掉的设备。

### 远端指挥设备（第 2 周）

5. 点「重新采集」→ 四阶段时间线依次点亮（受理 → 下发 → 设备接收 → **执行结果**）
6. 底部显示「下发前 N 条 → 下发后 M 条」，表格里带「指令」标记的行整行高亮
7. **点「暂停周期上报」** → 页面上数据年龄不再增长，但显示的是「已暂停 · 心跳 N 秒前」
   （不是「未更新」）。此时再点「重新采集」：**新出现的记录 100% 来自指令**
8. **演示「失败」**：服务器加 `--fault-injection` 启动，注入几次故障再点「重新采集」 →
   时间线第 4 步变红，显示「设备回报执行失败：N 条全部上报失败」并带原因
9. **演示「重复点击」**：连点「重新采集」→ 只受理一条，其余在提示区显示
   「上一次还没走完，已改为继续跟踪 `CMD-…`」；两个标签页同时点也一样（闸门在服务器）
10. **演示「超时」**：拔掉板子电源再点 → 约 30 秒后第 2 步变红「超时（设备未取走）」

第 7~10 步覆盖了任务卡要求的**完成 / 失败 / 超时三种结局**，以及「刷新 vs 重新采集」
在数据层的区别。三种结局必须分开看，因为它们要查的地方完全不同（见
[`docs/design/10-指令状态机与状态图.md`](docs/design/10-指令状态机与状态图.md)）。

### 现场的人与设备交互（第 3 周）

7. **直接按板子上的 MENU / PLAY / UP+ / DN−** → 板上的绿灯**先短亮一下**（本地反馈）
8. 紧接着看网页「求助」分区 → 出现这次求助：哪个键、几秒前、三级反馈逐级点亮
9. 表格里带「按键 MENU」标记的行与「定时」行用不同底色区分

第 7 步是这一周的重点：**反馈发生在两个地方** —— 手上的灯和屏幕上的记录，
而且两者都指向同一次真实的物理操作。

### 用一句话查数据 / 让设备再采一次（第 4 周）

打开「语言」分区，可以直接点示例按钮，也可以自己输入。
（本节用 ①~⑥ 编号，避免与上面已有的连续编号撞车）

① 点「**查看上次数据**」→ 回答里给数值、**这条记录自己的时间**、来源（设备 + 记录 id）。
   界面右侧元信息显示 `意图 query_latest | 工具 read_latest`。
   **库里的采集记录数不会增加** —— 读就是读。
② 点「**重新采集一次**」→ 回答里给请求 id（`CMD-…`）、状态 `done`、新入库条数。
   元信息变成 `意图 request_recollect | 状态 done | 新观测 12 条`。
③ **同一台设备连做 ①②两步** → 对比两个时间：① 是旧时间且**不会刷新**，
   ② 才会出现更新的时间。这是"读已有"和"要新的"最直接的区别。
④ 点「**看看数据吧（含糊）**」→ 助手**不执行任何动作**，反问你两条路怎么选
⑤ 点「**问坐标（越界）**」→ 明确回答"没有定位数据源"，**不会编一个经纬度给你**
⑥ **演示语言服务挂掉**：停掉 Ollama 再发一句 → 回答"语言模型服务暂时不可用，
   没有执行任何采集动作"，并打出结构化样例。**不会瞎猜一个意图去执行**

序号 ⑤ 对应任务卡里那句「无位置或过期位置须说明不足，不能生成坐标」：
这台板子上没有定位传感器，所以不是"暂时查不到"，而是**根本没有这类数据**。

> 演示前先跑 `week1\启动语言服务.bat`，确认 `/api/tags` 能看到 4 个模型。
> 直接开 Ollama 托盘程序会因模型路径问题导致全部意图解析失败（见第四节末）。

## 十二、本组相对通用示例的关键改动

1. **QMA6100P 裸驱动**：按数据手册自行实现 I2C 读写与 14 位补码数据组装，未依赖官方 BSP 组件
2. **型号勘误**：原理图标 QMA7981，实装为 QMA6100P（已通过 CHIP_ID=0x90 与 6 个特有寄存器自检确认），固件上电自动打印证据
3. **摄像头异步 handler 改造**：绕开 ESP-IDF 单线程 httpd 被 MJPEG 死循环堵死的致命问题
4. **摄像头服务器中转**：板端连接数从 N 降到 1，支持多人同时观看，并带三层断流自愈
5. **固定频率上报 + 服务端 stale 判定**：页面可证明「数据停了」
6. **服务端零依赖 + 幂等列迁移 + 容量上限自动裁剪 + CSV 范围导出**
7. **静态噪声基线分析**：用实测数据回答「板子没动为什么数值还在跳」
8. **下行指令搭车上行响应**：不给板子开监听端口、不引入 MQTT/WebSocket，指令随 1Hz 上报的响应体捎带下发
9. **四阶段回执状态机**：issued → delivered → received → done，超时还分 `accept`/`exec` 两段，故障可定位
10. **数据自带触发来源**：`trigger` 三态 + `request_id` + `button`，让「这批数据是这次动作新采的」成为数据库里的直接关联
11. **实体按键走 ADC 电阻梯**：四个键只占 GPIO1；按键电压实测与原理图偏差 ≤20 mV
12. **本地反馈用灯效序列**：单色灯 + 队列化灯效任务，用闪法区分"按到了/服务器收到了/没送出去"
13. **观测工具自身会改变被测对象**：串口工具默认拉高 DTR/RTS 会把 ESP32-S3 复位，导致 200 秒采集空白 —— 已修并写成排错案例

详细过程与踩坑记录见 [`docs/design/07-排错记录.md`](docs/design/07-排错记录.md)。

## 十三、关于本仓库的提交历史

**这一点需要说明清楚：本仓库的 Git 历史是开发完成后回溯重建的，不是开发过程中实时提交的。**

开发期间本项目**没有使用 Git**。为了让考核能看到完整的开发过程，我们在学期末用开发过程中留下的三类原始记录重建了提交历史：

| 重建依据 | 内容 |
|---|---|
| 工具会话记录 | 每一次改动的**精确时间戳**（精确到毫秒）与**涉及文件清单** |
| 文件变更快照 | 每个文件在当时**是什么内容**（全文快照，非推测） |
| 每日工作日志 | 当天做了什么、为什么这么做、踩了哪些坑 |

重建结果的可验证性：

- 每个提交的**时间**取自真实记录的毫秒时间戳，不是编造的日期
- 每个提交里文件的**内容**是对该文件当时快照的还原；重建完成后，整个工作树与开发结束时的实际文件做过**逐字节比对，249 个文件全部一致**（本节与上面「分支与周次对照」一节，都是在这次逐字节校验之后才补写的）
- 提交信息中的技术结论均可追溯到 [`docs/design/`](docs/design/) 与 [`docs/ai-conversations/`](docs/ai-conversations/) 中的对应记录

因此这份历史**如实地反映了工作的先后顺序与内容演化**，但**提交时间点本身是事后对齐的**，不代表当时执行过 `git commit`。

有两处改动在记录中没有留下变更痕迹，是按当日工作日志定位后补入对应提交的：`week1/观测记录.md` 的型号勘误同步（9-10）、`week1/firmware/esp32_imu/main/CMakeLists.txt` 加入 `camera_stream.c`（9-11）。
