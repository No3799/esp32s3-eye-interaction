# 09 · 实体按键与本地反馈闭环

第 3 周的目标：让**现场的人**也能触发采集，并把"我按了"这件事同时反馈在**本地**（板子上的灯）
和**远端**（网页）。第 1 周解决了"数据能不能拿回来"，第 2 周解决了"远端能不能指挥设备"，
这一周解决的是"**站在设备旁边的人**能不能和它交互，以及他能不能立刻知道自己按到了"。

---

## 1. 先说硬件事实（这次没有靠猜）

本项目在 IMU 型号上吃过"想当然"的亏（原理图写 QMA7981、实装是 QMA6100P）。
所以这一周动手前先把两块硬件查清楚，全部有出处。

### 1.1 四个用户按键：不是四个 GPIO，是**一条 ADC 上的电阻梯**

原理图第 4 页标注：

```
4-Keys: ADC1_CH0
MENU  2.41V   PLAY  1.98V   DN-  0.82V   UP+  0.38V
```

ESP32-S3 的 `ADC1_CH0` 就是 **GPIO1**。四个键按下时把分压点拉到不同电压，
固件靠读电压区分按的是哪一个 —— **四个键只占一个引脚**。

| 按键 | 原理图设计值 | 实测值（本板，2026-09-20） | 偏差 |
|---|---|---|---|
| UP+ | 380 mV | **367 mV** | −13 mV |
| DN− | 820 mV | **802 mV** | −18 mV |
| PLAY | 1980 mV | **1981 mV** | +1 mV |
| MENU | 2410 mV | **2409 mV** | −1 mV |
| 无人按键 | ≈3300 mV | **3162 mV** | — |

实测与设计值偏差都在 18 mV 以内，设计值可信。核验工具：`tools/btn_probe.py`。

判读用**就近归并**：取相邻两档的中点当判决边界。最小档间距 430 mV，
中点判决留下的余量足够覆盖上面这些偏差。

```
        UP+        DN-             PLAY      MENU
        367        802             1981      2409            3162(空闲)
   0 ────┼──────────┼───────────────┼─────────┼───────────────┼──── 3300 mV
        600        1400            2195      2855
      （判决边界 = 相邻两档中点）
```

### 1.2 本地反馈只能用 LED —— 而且这颗灯有硬性约束

官方《ESP32-S3-EYE 用户指南》原文：

> **Module Power LED**：… Software can configure **GPIO3** to set different LED statuses
> (turned on/off, flashing)… Note that **GPIO3 must be set up in open-drain mode.
> Pulling GPIO3 up may burn the LED.**

三条结论：

1. 本板**没有蜂鸣器**（只有输入用的数字麦克风，没有扬声器）
2. 本板**没有可编程 RGB 灯**（官方 BSP 能力表里 LED 走的是 `led_indicator`，驱动的是这颗单色灯）
3. 唯一软件可控的发光器件是 **GPIO3**，且**必须开漏输出、不得上拉**

所以固件里 LED 只用 `GPIO_MODE_OUTPUT_OD`，并且只做"拉低点亮"，永远不驱动为高电平：

```c
gpio_config_t cfg = {
    .pin_bit_mask = 1ULL << LED_GPIO,
    .mode         = GPIO_MODE_OUTPUT_OD,   /* 开漏，官方要求 */
    .pull_up_en   = GPIO_PULLUP_DISABLE,   /* 绝不上拉 */
    ...
};
static void led_raw(bool on) { gpio_set_level(LED_GPIO, on ? 0 : 1); }
```

> **这两条也修正了项目早期文档里的一处错误**：`docs/design/02` 原先把"按键 6 个"
> 与"没有本地反馈手段"写得含糊。实际是 4 个可用用户键（另加 BOOT / RST）+ 1 颗软件可控绿灯。

### 1.3 灯效语义

灯效是**唯一"写代码的人不在现场就无法验证"的输出**，所以开机先自证一次。

| 时机 | 灯效 | 含义 |
|---|---|---|
| 上电 | 连闪 3 次 | 自检：灯是活的、极性是对的 |
| 检测到按键 | 短亮 60 ms | 本地反馈："按到了" |
| 整批全部上传成功 | 连闪 2 次 | 远端反馈已闭环："服务器收到了" |
| 有上报失败 | 快闪 5 次 | "没送出去" |
| **开始录音**（BOOT） | 短亮 → **常亮** | **灯亮着 = 正在录** |
| **结束录音**（BOOT） | 灭 → 短闪 2 次 → 灭 | 灯灭了 = 录完了，接着上传 |

**录音这两条是 2026-10-29 补的**，起因是操作者反馈"看不出这次按键是开始还是结束"：

- 原来开始录音借用的就是"检测到按键"那一下短亮 —— 和按 MENU 求助**完全一样**；
  结束录音**没有任何灯效**，直接黑着。
- 现在的主判据是**稳态而不是节奏**：光看"灯亮着没有"就能回答"现在在不在录"，
  不需要数闪了几下。开始与结束互为镜像（暗→常亮 / 常亮→暗），节奏只在变更瞬间出现。
- 录音期间如果按了四个求助键，灯效会插进来播并以"灭"收尾 ——
  所以加了 `s_led_hold`：别的灯效播完自动把灯补亮，只有 `REC_STOP` 允许它灭。
  否则"亮着=正在录"会被一次求助按键打断，这个信号就不可信了。

## 2. 固件设计

### 2.1 任务划分：为什么采集不放按键任务里

```
btn_task (prio 5, 50Hz 轮询 ADC)
    │  消抖 → 判定键位 → 亮灯 → 投递事件
    ├──────────────────────────────► led_q ──► led_task (prio 4) ──► GPIO3
    └──────────────────────────────► btn_q
                                        │
app_main 主循环 ── 非阻塞取 ────────────┘
    │  取到就执行一次「按键采集批次」
    └──► HTTP POST（全工程唯一使用 HTTP 的地方）
```

三个刻意的选择：

**① 灯效走队列，不在按键任务里直接延时闪灯。**
如果按键任务里写 `vTaskDelay(60)` 去闪灯，这 60 ms 内它不再轮询 ADC，
期间的按键会丢。改成"投递灯效 → 专门的 led_task 串行播放"，
调用方立刻返回，多个灯效请求也不会互相交错打乱节奏。

**② 按键采集放在主循环，不放按键任务里。**
HTTP 上报全工程只有主循环一个使用者。若让按键任务也发 HTTP，
两个任务会争用 `seq` 与 `http_client` 句柄。代价是被按键打断的那一次
定时上报会晚一点 —— 这个代价我们用数据量出来了（见下节 `press_delay_ms`）。

**③ 消抖 + 边沿触发。**
每 20 ms 读一次 ADC，连续 3 次判读一致（60 ms）才认账；
只在"无键 → 有键"的跳变时触发一次，所以**长按不会连续触发**。

### 2.2 三种触发方式在数据层是分开的

第 2 周已经用 `request_id` + `trigger` 把"新采集"和"历史记录"分开了。
第 3 周在同一套机制上加了第三种来源：

| 触发方式 | `trigger` | `request_id` | `button` | 有下行通道吗 |
|---|---|---|---|---|
| 定时上报 | `timer` | `NULL` | `NULL` | — |
| 网页下发指令 | `command` | `CMD-20260920-0002` | `NULL` | 有（服务器搭车下发） |
| **板载实体按键** | `button` | `BTN-1a2b3c-MENU-0001` | `MENU` | **没有** |

最后一列是关键：**实体按键根本不存在"服务器受理"和"指令下发"两步**，
所以网页上给按键事件画四阶段时间线就是伪造证据。这是两条方向相反的路径：

```
网页下发指令： 网页 ──► 服务器(受理/下发) ──► 设备 ──► 服务器(记录完成)
                        ↑ 4 段都有服务器侧证据

板载实体按键： 人 ──► 设备 ──► 服务器(记录) ──► 网页
                      ↑ 起点在设备，没有"受理/下发"两段
```

### 2.3 按键响应速度是被测量出来的，不是声称的

按键批次的第一条数据带 `press_delay_ms` = 按下瞬间 → 本条采样组装完成 的毫秒数。
这个数字会**如实暴露架构的代价**：因为主循环可能在等一次 HTTP 响应
（超时上限 2 s），按键要等它回来才轮得到。所以这个值在几十毫秒到 1 秒多之间浮动。

这不算好看，但它是真的。要压低它，正确做法是把 HTTP 挪到独立任务，
用队列串起来 —— 那是第 2 周记录过的"已知限制"之一，留待后续。

## 3. 踩到的坑：事件 id 必须跨重启唯一

### 3.1 现象

第一版固件用内存里的计数器生成事件 id：

```c
snprintf(evid, sizeof(evid), "BTN-%s-%04lu", btn_name(btn), ++s_btn_n);
```

服务器按 `request_id` 聚合成"一次按键"。结果两次不同时间按的 UP+ 都是
`BTN-UP+-0001`，被**合并成同一条事件**：

```
BTN-UP+-0001   UP+  样本=10  跨度=105250 ms      ← 应该是 样本=5 跨度≈2s
```

### 3.2 根因

`s_btn_n` 是内存里的静态变量，**板子一重启就归零**。
而服务器是按 id 跨全表聚合的，于是两次按键被当成同一次。

### 3.3 修复

给事件 id 加一个**上电随机前缀**：

```c
static uint32_t s_boot_nonce = 0;
if (s_boot_nonce == 0) s_boot_nonce = esp_random() & 0xFFFFFF;   /* 24 位 */
snprintf(evid, sizeof(evid), "BTN-%06lx-%s-%04lu",
         (unsigned long)s_boot_nonce, bname, (unsigned long)(++s_btn_n));
/* → BTN-1a2b3c-MENU-0001 */
```

不用日期时间是刻意的：板子没有 RTC，绝对时间统一由服务器的 `server_ms` 提供。

### 3.4 这个坑值得单独记一笔的原因

它产出的不是"没有数据"，而是**看起来像证据、实际是错的**数据 ——
样本数 10、跨度 105 秒，如果不去核对，会直接被当成"一次按键采了 10 条、用了 105 秒"写进报告。
**错的证据比没有证据更危险**，这正是本项目一直在防的那类问题。

服务器侧的接口因此也做了一道保险：`/api/buttons` 的每条事件都给出
`first_id ~ last_id` 与 `span_ms`，跨度异常大时人一眼就能看出来。

## 4. 另一个坑：串口工具把板子复位了

第一版 `btn_probe.py` 用 `serial.Serial('COM5', 115200)` 打开串口，
**200 秒里一个字节都没收到**。当时板子其实活得好好的（服务器一直在收数据）。

根因：pyserial 打开串口时**默认拉高 DTR 和 RTS**，而 ESP32-S3 上这两个信号的
组合会触发芯片复位/进入下载模式。于是：

1. "打开串口"这个动作本身把板子重启了
2. 芯片重启 → USB 重新枚举 → Windows 下**旧句柄静默失效**（不报错，只是再也读不到数据）
3. 用户的按键照常被固件处理并上传（所以服务器有数据），但串口侧一无所获

修复两处：

```python
s = serial.Serial(port, 115200, timeout=0.3)
s.setDTR(False)      # 不拉 DTR/RTS，避免触发复位
s.setRTS(False)
```

外加一个**看门狗**：连续 5 秒读不到数据就关掉重开串口，自动从"重新枚举"里恢复。

**教训**：调试工具本身也会改变被测对象的状态。这次是工具复位了芯片，
下一次可能是工具占用了引脚、改写了寄存器。**"观测不到"要先怀疑观测手段，再怀疑被测对象。**

## 5. 接口变化

### 5.1 新增字段（`POST /api/data` 请求体）

| 字段 | 含义 |
|---|---|
| `button` | 按的是哪个键：`MENU`/`PLAY`/`UP+`/`DN-`；非按键触发为 `null` |
| `press_delay_ms` | 按下 → 本条采样组装完成 的毫秒数；仅按键批次首条带 |

数据库新增两列 `button` / `press_delay_ms`，走原有的幂等 `ALTER TABLE` 迁移，
**老数据一行不丢**（老行的新列为 NULL，网页显示时按"没有"处理）。

### 5.2 新增接口

```
GET /api/buttons?limit=10[&device_id=…]
```

按 `request_id` 聚合出"一次按键 = 一条事件"：

```json
{
  "count": 4,
  "events": [{
    "event_id": "BTN-1a2b3c-MENU-0001",
    "button": "MENU",
    "samples": 9,
    "first_id": 25955, "last_id": 25963,
    "first_time": "2026-09-20 15:02:11",
    "span_ms": 1929,
    "press_delay_ms": 37,
    "age_seconds": 12.4
  }]
}
```

为什么单开一个接口而不塞进 `/api/commands`：那是两条方向相反的路径（见 2.2），
硬塞进同一张表会让"阶段"字段一半是空的，反而看不清。

## 6. 已知限制

| 限制 | 说明 | 影响 |
|---|---|---|
| 按键响应要等 HTTP | 主循环在等上报响应时无法立刻处理按键 | `press_delay_ms` 会波动到秒级 |
| 只认单键 | 四个键同时按下会落到电压最近的那一档，不区分组合键 | 无组合键功能 |
| 无长按/双击 | 只在"抬起→按下"边沿触发一次 | 长按只算一次 |
| 灯效无优先级 | 队列满（8 条）时新灯效被丢弃 | 连按极快时可能少闪一次，不影响数据 |
| 事件 id 未与服务器对账 | 服务器不校验 id 格式，纯靠设备保证唯一 | 设备侧随机前缀撞车概率 ~1/1.7e7 |
| 历史污染未清理 | 修复前的 45 条记录仍留着旧的、会误合并的 id | 保留为排错证据，见 3 节 |
