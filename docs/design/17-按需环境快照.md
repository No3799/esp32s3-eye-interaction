# 17 · 按需环境快照

> 第 7 周。「用户请求查看环境时，系统如何说明采集是否成功，采到的是哪一时刻的画面？」

## 0. 一句话

**拍一张图不难，难的是让"这张图是什么时候拍的、是不是这一次拍到的"没有歧义。**

所以这一周的产出不是"能截一张图"，而是一条记录：每次请求都有编号、有拍摄时刻、
有判定结果；失败就是失败，绝不拿上一张顶着。

## 1. 只做按需，不做定时抓拍

任务卡原话：「只在请求或教学事件触发后取图」。

落到代码里就是 `trigger` 只接受三个值：

| trigger | 含义 | 谁发起 |
|---|---|---|
| `user` | 人在页面上点了「拍一张」 | 用户 |
| `help_event` | 教学求助事件触发 | 系统，但事件本身是人按的 |
| `replay` | 回放历史图像（不碰设备） | 用户 |

传别的值 → **拒绝并留一条 `denied` 记录**（HTTP 403）。
"没有明确请求不取图"因此是可测的，不是一句承诺（验收脚本 S1 就是测这个）。

## 2. 一张图的生命周期

```
POST /api/snapshot {trigger, request_id}
        │
        ├─ 无 trigger ──────────────► denied（403，也落记录）
        ├─ 找不到板子 IP ──────────► board_unknown
        ├─ GET http://<板子>:81/capture
        │      ├─ 连不上 ──────────► unreachable
        │      ├─ 超时 ────────────► timeout
        │      └─ HTTP 错误 ───────► board_error
        └─ 拿到字节 → 判定 → ok / too_dark / flat_frame / too_small / bad_jpeg
```

字段（`data/snapshots/index.jsonl`，一行一条）：

| 字段 | 作用 |
|---|---|
| `id` | `SNAP-YYYYMMDD-HHMMSS-xxxx`，**失败记录也有编号** |
| `request_id` | 关联是哪一次请求触发的 |
| `captured_at` / `captured_ms` | **拍摄时刻**（服务器收到画面的时间） |
| `trigger` / `authorized_by` | 谁让它拍的 |
| `latency_ms` | 从发起到收完，多少毫秒 |
| `status` / `usable` / `reason` | 判定结果与原因 |
| `width` / `height` / `bytes` / `sha256` | 图像本身的可核对信息 |
| `source` | `device`（真拍）或 `replay`（回放） |
| `file` | 图在 `data/snapshots/` 下的文件名 |

> **为什么用 JSONL 不用 SQLite**：这些是"一张一张的证物"，顺序追加、按时间读，
> 用文本就能查。真正的业务表（readings / commands / help_events）仍然在 SQLite 里。

## 3. 判定：先认 JPEG，再谈亮度

判据顺序（顺序本身是一个坑，见 §3.1）：

1. 有没有 JPEG 头（`FF D8`）→ 没有就 `bad_jpeg`
2. 能不能解码 → 解不开就 `bad_jpeg`
3. 分辨率是否 ≥ 160x120 → 否则 `too_small`
4. 平均亮度 < 12 → `too_dark`（镜头被遮挡 / 没开灯 / 全黑）
5. 灰度标准差 < 3 → `flat_frame`（几乎是纯色）

用 PIL 解码后算两个统计量。这是**启发式**，不是目标检测；判错时能指到具体数值，
所以不至于变成"系统说不能用，但我不知道为什么"。

### 3.1 一个被单元测试抓出来的顺序错误

第一版把"字节数 < 3000 就判不可用"放在最前面。看起来很合理（正常 QVGA JPEG 10~40KB），
但**全黑画面恰恰压缩得极小**（320x240 纯黑 JPEG 只有约 1.5KB）。

于是"镜头被挡住"会被判成 `too_small` —— 一个是遮挡，一个是分辨率不对，
处置完全不同（前者去看镜头，后者去查配置）。

现在字节数只做兜底（< 200 字节连 JPEG 头都不够），可用性由解码后的统计量决定。

> 教训：**判据的先后顺序也是逻辑的一部分。** 先命中哪个条件，决定了错误被归到哪一类。

## 4. 四种反馈（界面）

| 状态 | 界面文字 | 画面区 | 用户该做什么 |
|---|---|---|---|
| 采集中 | 「采集中…」 | 保留上一张？**不**，先显示"正在取一帧" | 等 |
| 采集成功 | 「采集成功」+ 尺寸 / 拍摄时刻 / 耗时 | 换成本次的新图 | 无 |
| 画面不可用 | 「画面不可用」+ 亮度或方差数值 | **显示这张不可用的图** | 看镜头是否被挡、是否没开灯 |
| 采集失败 | 「采集失败」+ 原因 | 有上次成功就显示它，**并写明"不是本次"**；没有就清空 | 查网络/板子 |

第 3 行容易做错：拍到了但不可用时，如果只写"失败"，人会以为是网络问题。
**把那张不能用的图显示出来**，比任何文案都直接。

## 5. 保留策略：最多 50 张，但最近一张成功图不删

两种情况都会出事：

- 删太多 → 连"上次成功"都没了，§6 那条规矩就没法执行
- 不删 → 磁盘一直涨

所以 `_prune()` 是"最多 `MAX_KEEP=50` 张，**例外**：最近一张 `source=device` 且 `status=ok`
的记录永不删除"。例外不是心软，是让 §6 可执行。

## 6. 当堂验证：上次成功不得被标为本次

这是整周最核心的一条，落到三个地方：

1. **接口层**：`is_this_attempt` 只有在 `status=ok` **且** `source=device` 时才为 `true`。
   回放即使 `ok` 也是 `false`。
2. **文案层**：失败时若引用上次成功，回复里必须出现"那不是本次采集的结果"，并带上它自己的拍摄时间。
3. **界面层**：旧图放在画面区时，旁边写"上次成功（时间，N 秒前）—— 不是本次采集的结果"。

验收脚本 S5 用 `force_ip` 注入一次必失败（该字段只在 `--fault-injection` 下生效），
断言这三点同时成立。

## 7. 备用路径：回放

任务卡：「用获授权的真实历史图像练习，标为回放；随后补验一次真实按需采集」。

- 回放只允许导入 `debug_logs/` 下的历史抓帧（其它路径一律 403，防止变成任意文件读取）
- 记录里 `source=replay`、`imported_from` 指向源文件、`sha256` 可核对
- **拍摄时间不知道就写不知道**，不拿导入时间冒充
- 回放**不计入** `last_ok` —— 否则"上次真的拍到了"会被误解

## 8. 个人项目：图像采集的触发与停止条件

任务卡「提交与迁移」要求明确这两条。这个项目的答案是：

**触发**（满足任一）
- 用户在页面点「拍一张」
- 教学求助事件发生（人按下按键求助）

**停止**（满足任一即停）
- 没有明确 trigger → 直接拒绝
- 连续 3 次采集失败 → 停止自动重试，等人处理（避免对着一块坏掉的板子狂发请求）
- 本板**没有定时抓拍**，所以不存在"忘了关"的情况

**不做的事**（明确写下来，免得以后被当成遗漏）
- 不拍人脸、不拍私人空间：这块板没有云台、固定朝向桌面，教学场景由教师准备
- 不做视频录制：只取单帧，避免"一直在录"的隐私问题
- 不做人脸/目标识别：本周只回答"有没有拍到、画面能不能用"，不回答"拍到了什么"

## 9. 已知限制

1. **没有真机遮挡实测**：`too_dark` / `flat_frame` 的判断用合成图覆盖（全黑、纯色），
   没有真去用手挡住镜头拍一次。判据本身被测过，但"真遮住时阈值够不够灵敏"未验。
2. **`captured_at` 是服务器收到画面的时间**，不是传感器曝光时刻。板子没给时间戳，
   两者在本局域网内相差约 1.6 秒（含取帧 + 传输），已在记录里体现为 `latency_ms`。
3. **单帧与 MJPEG 流共用摄像头**：两者同时取帧时，`/capture` 可能等到下一个空闲缓冲，
   表现为偶发慢一点（实测 1.6 秒，通常 < 1 秒）。
4. **回放不等于真实采集**：`last_ok` 刻意排除回放，所以只有回放时界面会说"此前还没有成功过"。
