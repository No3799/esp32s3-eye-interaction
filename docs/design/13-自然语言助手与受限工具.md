# 13 · 自然语言助手与受限工具（第4周）

> 面向问题：「查看上次数据」和「重新采集一次」应怎样映射为不同任务，
> 并使用前两周已验证的接口？
>
> 代码：`week1/server/nl_agent.py`（助手本体）、`week1/server/server.py` 的 `/api/ask`
> 与 `/api/agent/info`、`week1/web/index.html` 的「语言」分区。

---

## 1. 三个角色，必须分清

任务卡「前2学时」的第一句就是「区分开发助手与产品运行时模型」。这不是名词解释，
它决定了权限边界 —— 混起来用，就会把"写代码的 AI"当成"产品里的 AI"。

| | ① 开发助手 | ② 产品运行时模型 | ③ 受限工具 |
|---|---|---|---|
| 是谁 | 写这份代码的 AI（IDE / WorkBuddy 里的助手） | 部署在服务端的预训练语言模型<br>本项目：本地 Ollama 的 `qwen3.8-q2` | 服务端函数<br>`read_latest` / `request_recollect` |
| 能看到什么 | 整个磁盘、终端、代码、数据库 | **只有**用户那一句话 + 系统提示 | 数据库连接、指令状态机 |
| 能做什么 | 改代码、跑命令、装环境 | 只输出一个 JSON：意图 + 参数 | 读一条记录 / 下发一条指令 |
| 权限 | 极大 | 极小 | 恰好够用 |
| 出错后果 | 代码错，改回来 | 判错意图 | 下错指令，**会动硬件** |

**为什么要把 ② 压得这么窄？**
因为单元2的难点是「概率性语言输出 → 确定性任务执行」。
语言模型天生会"把话说圆"，如果让它自由生成答案，它会说「已采集成功」——
而设备可能压根没回执。所以本项目里，模型的输出**只被当作参数**，
不被当作结论。

具体到代码：

```python
# nl_agent.py · handle()
parsed = self.llm.chat_json(INTENT_SYSTEM, "用户说：" + text)   # 只拿意图+参数
intent = parsed["intent"]                                     # 白名单校验
device_id, note, ids = self._resolve_device(parsed["device_id"])  # 设备范围校验
tool_res = self.read_latest(device_id)  或  self.request_recollect(...)  # 受限工具
reply = self._reply_read_latest(tool_res, note)               # 服务端拼装事实
```

**答案里的每一个事实都由服务端从工具返回值取，模型不参与。**

## 2. 两种任务如何映射到前两周已验证的接口

| 用户的话 | 意图 | 调用的工具 | 复用的**已验证**接口 | 是否产生新数据 |
|---|---|---|---|---|
| 查看上次数据 / 现在多少 | `query_latest` | `read_latest` | 第1周的 readings 表与 `/api/latest` 同一份查询逻辑 | **否** |
| 重新采集 / 再采一次 | `request_recollect` | `request_recollect` | 第2周的 `CommandStore`（指令状态机 + 捎带下发 + 回执） | **是** |

关键：**没有重写任何底层通信**。第4周只是在已验证的两条路径上各加了一个入口。
端侧仍是真板子（ESP32-S3-EYE）按原协议上报与执行，一行固件都没改。

### 2.1 意图的判定规则（写进提示词，也写进文档）

```
"查看/显示/读/是多少/最近/上次" 且没有"重新/再/新采"  → query_latest
"重新采集/再采一次/重新取/刷新数据/现在采一次"        → request_recollect
只是问"能不能/好不好/怎么用"                          → unclear（澄清）
问位置、坐标、经纬度、GPS、你在哪                     → unsupported（说明不足）
```

模型给的意图还要过**服务端白名单**：不在 `{query_latest, request_recollect,
unsupported, unclear}` 里的一律降级成 `unclear`。模型不能凭空发明第三种任务。

## 3. 受限工具：三处收紧

### 3.1 参数限幅

`request_recollect` 的 `samples` / `interval_ms` 与第2周网页按钮**共用同一套限幅**：

```python
SAMPLES_MIN, SAMPLES_MAX = 1, 100
INTERVAL_MIN, INTERVAL_MAX = 20, 1000
```

越界不是静默改掉，而是**在回答里说明改了**：「参数越界已限幅：samples 500 → 100」。
用户说"采 500 个点"，系统只采 100 个却不说，那就是在骗人。

### 3.2 设备范围

设备范围的**唯一真相**是数据库里真实出现过的 `device_id`。模型说出来的名字必须能落到它上面。

这里踩过一个真实的坑：库里有一台第1周数据模拟器 `selftest-sim`（68 条，9/23 后再没上报）。
第一版把"库里出现过的所有设备"当范围，于是"查看上次数据"变成歧义
（有两台设备，得让用户指明），而用户明明只有一台真板子。

所以改成按**活跃度**区分：

```python
ACTIVE_WINDOW = 300.0   # 5 分钟内有上报才算"当前设备"

· 未指明设备 → 只在**活跃设备**里选；只有一台就用它，多台才澄清
· 明确点名   → 在**全部已知设备**里匹配（查历史本来就该查得到历史）
· 采集操作   → 额外要求设备活跃；给一台离线板子下指令只会白等到超时
```

### 3.3 歧义处理

三种歧义，三种处理，都**不猜**：

| 歧义 | 表现 | 处理 |
|---|---|---|
| 意图歧义 | 「看看数据吧」 | 返回 `unclear`，列出两个可选项让用户挑 |
| 设备歧义 | 多台活跃设备且没指明 | 拒绝执行，列出设备名 |
| 在途冲突 | 上次采集还没走完 | 不开新的，回传在途请求 id 与状态 |

## 4. 没有完成证据，就不许说"已采集成功"

这条是本周的**硬要求**，用了三层独立的防线，任何一层失效都不会漏。

### 第一层：模板由服务端拼装

回答的骨架是代码写的，事实槽位填工具返回值：

```python
if st == "done" and tool_res["has_completion_evidence"]:
    lines.append("采集已完成（设备回执 + 新观测入库，两项证据齐全）。")
elif st == "failed":  → "采集**失败**：设备回报了失败，没有完成证据。"
elif st == "timeout": → "采集**超时**，没有完成证据。"
else:                 → "采集请求已下发，但**还没有完成证据**（当前状态 issued）。"
```

注意 `has_completion_evidence` 的判据是**两项同时成立**：

```python
has_evidence = (status == "done" and samples_in_db > 0)
```

- 只有回执说 done、库里没记录 → 不算（回执可能是迟到的旧报文）
- 只有库里有记录、回执不是 done → 不算（记录可能来自别处）

### 第二层：断言闸门

即使将来有人改了拼装逻辑，还有一道独立检查：

```python
SUCCESS_CLAIM_PATTERNS = ("已采集成功", "采集成功", "已完成采集", "数据已更新", ...)

def _assert_evidence_gate(text, allowed):
    if allowed: return text, True, ""
    for p in SUCCESS_CLAIM_PATTERNS:
        if p in text: return text, False, f"无完成证据却声称「{p}」"
```

### 第三层：`_pack()` 里的二次保险

打包返回值前再查一遍工具结果，没证据就把回复里的成功声明清掉。
这一层与闸门独立，目的是防止"改了一处就漏了另一处"。

### 为什么不让模型润色措辞

默认 `NL_REPLY_STYLE=template`，模型**完全不参与措辞**。
可选的 `model` 模式会让模型润色，但润色结果必须过两关：

1. 过断言闸门（没证据时不许出现成功说法）
2. **数字不许变**（比较润色前后的数字集合，不一致就回退模板）

第 2 条是必需的：模型润色时很容易顺手把"12 条"写成"10 条"或把时间改掉。

## 5. 「无位置/过期位置」在本工程怎么落地

任务卡写着：「无位置或过期位置须说明不足，**不能生成坐标**」。

本工程的性质决定了这条的落法：**板子上没有定位传感器**。
只有 QMA6100P（三轴加速度计）、OV2640（摄像头）、一颗 LED、四个按键。
没有 GPS、没有北斗、没有 WiFi 定位。所以「设备在哪」这类问题，
系统**根本没有数据可答**。

两种"不足"分别处理：

| 情况 | 本工程的对应 | 回答 |
|---|---|---|
| **无位置** | 问坐标/经纬度/在哪 | 明确说「没有定位数据源」，列出能做的两件事，**绝不生成坐标** |
| **过期位置** | 读到的数据超过 `STALE_SECONDS`（默认5秒） | 在回答里标「⚠️ 这条数据已过期，反映的是历史值，不代表设备当前状态」 |

「不能生成坐标」是可测的：验收脚本用正则找坐标数字对
（`-?\d{1,3}\.\d{3,}\s*[,，]\s*-?\d{1,3}\.\d{3,}`），出现就判失败。
同时用正常读数（`X=-0.0083 g，Y=-0.2244 g`）做**反例**，确认探测器不会误报。

## 6. 密钥边界

```
NL_LLM_BASE_URL   语言服务地址（默认 http://127.0.0.1:11434）
NL_LLM_MODEL      模型名（默认 qwen3.8-q2:latest）
NL_LLM_API_KEY    密钥（本地 Ollama 不需要；换商用/校内服务时填这里）
NL_LLM_PROTOCOL   ollama | openai（默认自动判断）
```

三条规矩：

1. 只从**服务端环境变量**读，代码里没有硬编码密钥
2. `/api/ask` 与 `/api/agent/info` 的响应里**只有** `{host, model, protocol, has_key, timeout_s}`，
   `has_key` 是布尔值，不是密钥本身
3. 网页拿不到 base_url 和 key；它最多知道"用的哪个模型"

`LLMClient.public_info()` 里刻意只截主机名：

```python
host = re.sub(r"^https?://", "", self.base_url).split("/")[0]
```

因为完整 URL 里可能带 token（有些服务把 key 放在 query 里）。

## 7. 备用路径：语言服务挂了怎么办

任务卡要求「服务异常时使用结构化样例定位解析问题」。实现：

```python
except Exception as e:
    return {
        "ok": False, "error": "llm_unavailable",
        "reply": "语言模型服务暂时不可用，我没法判断这句话的意图，"
                 "所以没有执行任何采集动作。\n\n结构化样例（用于定位解析问题）：\n"
                 + json.dumps({...schema...}),
    }
```

要点：**不猜意图、不执行动作、把 schema 打出来**。
实测（把 `NL_LLM_BASE_URL` 指向不存在的端口）返回：

```
ok=False | error=llm_unavailable
语言模型服务暂时不可用，我没法判断这句话的意图，所以没有执行任何采集动作。
结构化样例（用于定位解析问题）：
{ "intent": "query_latest|request_recollect|unsupported|unclear", ... }
```

这段还有个副产品：它能区分「模型服务挂了」和「模型把意图判错了」——
前者是 `llm_unavailable`，后者是意图字段不对。两种故障的排查方向完全不同。

## 8. 接线方式（服务端）

```
POST /api/ask         {"text": "查看上次数据"}
                       → {ok, intent, device_id, reply, tool, tool_args,
                          tool_result, error, elapsed_s, llm, trace}

GET  /api/agent/info  → {llm:{host,model,protocol,has_key,timeout_s},
                         reply_style, tools, note}
```

`trace` 字段保留了每一步的判断（意图解析原始输出、设备解析结果、工具摘要），
出问题时不用猜是哪一步错了。它**不含**密钥。

## 9. 已知限制

- **语言服务依赖本机 Ollama**，且 0.40.3 的托盘程序读不到 junction 路径下的模型
  （`/api/tags` 返回空，日志刷 `bad manifest`）。必须用
  `week1/启动语言服务.bat`（显式 `OLLAMA_MODELS=D:\ollama\models`）启动。
  这是环境限制，不是助手的问题，但会让"意图解析全失败"看起来像助手坏了。
- **单轮，无上下文**。第6周才做短期任务上下文与澄清/取消。现在每句话独立解析，
  不能说"再来一次"指代上一句。
- **只有两个工具**。没有历史趋势查询、没有按时间窗查询的语音入口。
- **不做流式输出**。一次请求等模型跑完（热调用约 3~8 秒）才返回。
- **超时路径未在真板上复现**。真板子的 accept 超时在第2周验证过
  （CMD-20260918-0004，30.45 秒）；本周的 `nl_timeout_test.py` 用的是
  离线设备 `selftest-sim` 触发同一条服务器侧超时逻辑（30.5 秒），
  走的是**同一段** CommandStore 代码，但不是同一块硬件。
