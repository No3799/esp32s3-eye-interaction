# 15 · 语音任务的澄清与停止（第 6 周）

> 任务卡原文：
> 「系统听错了、用户改变主意或回答迟到时，如何保持交互连续？」
> 「实现澄清、重新输入、停止播报和回到空闲状态。」
> 「取消后迟到结果不得重新播放或触发动作；新任务不被旧任务结果覆盖。」

## 0. 一句话

**给每个任务一个代数（generation），迟到的结果一比对就知道该丢。**

语音交互最容易出的不是"识别错"，而是**时序错**：你说完 A，等不及又按了停止或改口说 B，
此时 A 的响应才回来 —— 如果不加判断，它会把 B 的界面盖掉、还会念出来。
这跟识别准不准无关，是状态管理的问题。

## 1. 状态机

```
        空闲 idle
          │ 发送 / 按 BOOT 录音
          ▼
   ┌─ 录音（仅语音入口）
   │      │ 结束录音
   │      ▼
   │   识别中 ──失败──► 出错（文字入口仍可用）
   │      │ 识别成功
   ▼      ▼
  执行中（/api/ask）
          │
     ┌────┴────┐
     ▼         ▼
   完成       已拒绝 / 出错
     │
     ▼
  播报中 ──► 空闲
```

任何时刻按「停止」或 Esc：**立刻回到「已取消」**，且把代数 +1。

## 2. 迟到结果怎么隔离：用代数，不用"记住被取消的 id"

```js
let gen = 0;

async function send(text) {
  const myGen = ++gen;              // 这次任务的代数
  const d = await fetch(...);
  if (myGen !== gen) return;        // 代数变了 → 我迟到了 → 丢弃
  ...渲染...
}
```

为什么不用"维护一个被取消的 id 列表"：

- 列表要**记得删除**，忘记删就永远丢；代数只增不减，天然不会漏
- 连续取消两次、取消后再发一次，用列表要处理组合；用代数只是一个 `!==`
- 服务端不需要知道谁被取消 —— 取消是**客户端对结果的处置**，
  而不是"让服务端别算了"（见第 4 节的边界）

判据只有一句：**响应回来时，我是不是还是"当前那个任务"**。

## 3. 停止 = 三件事，少一件都只是"看起来取消了"

```js
function stopAll(why) {
  gen++;                                  // 1) 在途响应立刻变成迟到
  ctl.abort();                            // 2) 断开连接，别让它挂着
  speechSynthesis.cancel();               // 3) 掐掉正在念的那句
  busy = false; 状态 = '已取消';            // 4) 界面回空闲
}
```

只做 2 不做 1：`fetch` 被中止会抛 `AbortError`，但如果响应恰好已经到浏览器，
没有代数判断它仍会把结果画上去。
只做 1 不做 3：文字不更新了，**但声音还在念** —— 用户以为没停。
只做 1、2、3 不做 4：按钮还灰着，人没法马上问下一句。

## 4. 边界：服务端不可"中途取消"

「停止」是**客户端不再采用这个结果**，不是让服务器别执行。

- 读数据：停不停都一样（只读，无副作用）
- 请求采集：指令可能已经下发到设备。此时取消只是不看结果，
  **设备照样在采**。所以界面说的是"在途结果不会再出现"，不是"已撤销采集"

这条必须写清楚 —— 否则"取消"会被理解成"什么都没发生"，而设备其实已经动了。

## 5. 忙的时候又发一句：不能"没反应"

原来的实现是 `if (busy) return;` —— 消息凭空消失，人会以为丢了，于是一遍遍重发。

现在明确提示：**「上一个还在处理，先按停止」**，并且不发第二个请求。

为什么不做"自动取消旧的、发新的"：旧任务可能是一次采集，
自动取消会让"设备在采、但没人看结果"变成默认行为。让人**显式**按停止，才知道自己在放弃什么。

## 6. 时序测量口径

任务卡「后2学时」要求量「输入结束到首次反馈」和「输入结束到任务完成」。

| 指标 | 起点 | 终点 | 实测 |
|---|---|---|---|
| 首次反馈 | 提交（回车 / 结束录音） | 状态变成「处理中」 | **≈0 秒**（同一帧内），这本身就是结论：反馈是即时的 |
| 任务完成 | 提交 | 回答落地 | 3~8 秒（模型解析占大头，服务端 `elapsed_s` 单列） |

每条回答的元信息里带：`服务端 X 秒`（识别+工具）+ `总耗时 Y 秒`（含网络与模型），
两个数分开，才知道慢在哪一段。

## 8. 多轮：把一句短回答接回上一轮的问题

「看看数据吧」→ 系统追问「读已有记录，还是现在再采一次？」→ 用户只回一个字「看」。
**如果不记住上一轮问了什么，「看」永远是不清楚的。**

实现是三层都"有限"的记忆（`server/turn_context.py`）：

| 维度 | 取值 | 为什么 |
|---|---|---|
| 每个会话记什么 | **只记 1 条待答问题**（不是整段对话） | 要的是"我问了你什么"，不是聊天记录 |
| 存活时间 | **180 秒** | 半小时后说「看」不该接上上一轮 —— 过期是保护 |
| 会话数 | **最多 200 个**，按最久未用淘汰 | 内存不随访问量增长 |

### 8.1 为什么用规则接，不再跑一次模型

上一轮那句是**封闭式问题**（A 还是 B），答案空间只有两个。
用规则把「看」落到 `query_latest` 上：

- **更稳**：模型对孤零零的「看」这次可能给 A、下次给 B；规则不会
- **更快**：省一次 3~8 秒的模型调用
- 真正开放的话仍然走模型 —— 规则只处理"对封闭问题的短回答"

规则自己也有两道刹车，都是为了**宁可不猜**：

1. 长度 > 16 字 → 这多半是新的一句话，交回模型
2. 只命中单字别名（「看」「读」）且回答 > 4 字 → 交回模型（"看看设备在哪"不该被接成读记录）

### 8.2 一个被测出来的教训：判断"需不需要上下文"要先看模型

第一版测试用「查看」当反例，断言"没有上文就该判为不清楚"。
**跑出来是失败的** —— 模型自己就把「查看」判成了 `query_latest`，根本不需要上下文。

真正需要上下文的，是**单看必被判为不清楚**的词。实测：

```
看    → unclear       重新 → unclear       记录 → unclear
读一下 → query_latest  再采 → request_recollect
```

所以用例改成「看」和「重新」。**"我需要上下文"这个前提本身也要验证**，否则测的是自己想象的行为。

## 9. 已知限制

- **本机没有扬声器**：播报"有没有念"只能靠 `speechSynthesis.speaking` 与
  `boundary` 事件判定，听不到（见 `design/14` 与 `tools/check_tts.py`）
- **多轮上下文只记"一个问题"**：不是完整对话记忆，也没有指代消解
  （「那它呢」这类超短指代接不住，会回到追问）
- **半双工**：按一下说、再按一下结束，说话时系统不听、系统播报时不录音。
  这是本周的**基础形态**；任务卡把「唤醒词、回声消除、全双工」列为**拓展**，
  三项都没做 —— 它们各自需要额外的音频前端（VAD / AEC），不是界面能补的

## 10. 反悔后的安全恢复（本周迁移的规则）

任务卡「提交与迁移」要求「迁移一条『用户反悔后安全恢复』的处理规则」。
下面这条规则落在 `web/index.html` 的 `stopAll()` 里，三条一起才算"安全"：

| 规则 | 做法 | 如果不这么做 |
|---|---|---|
| ① **不自动重发** | 取消后只把话**填回输入框**，要发得自己再按一次 | 「取消」变成「稍后自动执行」，比不取消更危险 |
| ② **不留空手** | 填回原文并选中，省去重打 | 人反悔时得整句重敲，很容易干脆放弃 |
| ③ **说清边界** | 明确讲「设备指令不会被撤回」 | 用户以为停了，设备其实还在采 |

配套的判定：只有在**没有新任务接管**时才清掉原文（`myGen === gen`），
否则旧任务的一句话会把新任务的内容覆盖掉。

> ⚠️ **验证状态**：这三条已写进代码并通过 JS 语法检查，但**没有跑浏览器验证**
> （2026-10-29 下午暂停了浏览器自动化授权）。要判定为"已验证"，
> 需要跑一次：发出请求 → 按停止 → 确认输入框被填回、且没有第二个请求发出。
