## 一、这一周要证明什么

本周问题是「如何说明采集是否成功，采到的是哪一时刻的画面」。

一句话回答：**每次请求都是一条有编号的记录，成功与失败各有独立状态，
"上一次成功"永远带着它自己的时间，并且永远不会被当成这一次。**

三个关键值：

| 值 | 从哪来 | 为什么重要 |
|---|---|---|
| `is_this_attempt` | `status=ok` **且** `source=device` | 回放即使成功也不算本次，这是防止误读的第一道 |
| `captured_at` | 服务器收到画面的时刻 | 用户问"这是什么时候的"，答案必须具体到秒 |
| `latency_ms` | 发起到收完 | 让"慢"能定位：是板子慢还是网络慢 |

## 二、真机实测

```
S4 真采集（板子在线）
  HTTP 200  status=ok  is_this=True  320x240  1623ms
  reply: 拍到一张 320x240 的画面，拍摄时刻 2026-10-30 08:54:47，耗时 1623 ms。
  图片可回取：GET /api/snapshot/SNAP-20261030-085447-4502.jpg → image/jpeg
```

**1623 ms 的构成**：取帧（传感器 + JPEG 编码）+ WiFi 传输 + 服务器落盘。
对照第 1 周的观测（一次 HTTP POST 往返 0.5~2.5 秒），这个数量级是合理的，
没有额外引入等待。

## 三、当堂验证的现场

这一条值得单独留证据，因为它是"看起来对、其实错"的典型场景：

```
S5 注入必失败（force_ip=10.255.255.1，只在 --fault-injection 下生效）
  HTTP 200  status=timeout  is_this=False
  reply: 板子没在规定时间内回画面，**这次没拍到**：URLError: <urlopen error timed out>
         上次成功的一张是 SNAP-20261030-085447-4502（2026-10-30 08:54:47），
         **那不是本次采集的结果**。
```

三件事同时成立才算过关：状态是失败、`is_this_attempt` 是 false、旧图被引用时明确标注不是本次。
少任何一条，用户都可能把旧画面当成刚拍的。

## 五、一个被单元测试抓到的错误

第一版判定把"字节数 < 3000"放在最前面。看着合理，实际会出事：

| 输入 | 现象 | 第一版判定 | 正确判定 |
|---|---|---|---|
| 320x240 纯黑 JPEG | 只有约 1.5KB | `too_small`（太小） | `too_dark`（被遮挡） |
| 320x240 纯灰 JPEG | 约 1.8KB | `too_small` | `flat_frame`（纯色） |

**"镜头被挡住"和"分辨率不对"是两种完全不同的故障**，一个去看镜头，一个去查配置。
判据顺序错了，用户就会被指到错误的方向。

现在顺序是：认 JPEG → 解码 → 尺寸 → 亮度/方差；字节数只做兜底。

## 七、没做的与做不到的

1. **教师提供的教学场景与图像样例** —— 没有。用的是自己桌面的历史抓帧
2. **模型课的轻量视觉基线 / 标签定义** —— 没有。本周不涉及识别，只判"画面能不能用"
3. **端侧课提供按需图像接口** —— 没有。用板子已有的 `/capture` 自建，属替代
4. **界面未在真浏览器点过** —— 见第四节
5. **没有真机遮挡实测** —— `too_dark` / `flat_frame` 用合成图覆盖；
   真去用手挡住镜头拍一次还没做。判据被测过，"真实遮挡时阈值够不够灵敏"未验
6. **`captured_at` 是服务器收到画面的时间**，不是传感器曝光时刻（板子没给时间戳）
7. **单帧与 MJPEG 流共用摄像头** —— 同时取帧时偶发慢一些（实测 1623 ms）

## 九、这一周的一句话结论

**能按需拍到、能说清是不是这一次、失败时不会拿旧图顶着。**

具体说：一次真机采集 320x240 / 1623 ms；注入失败后 `is_this_attempt=false`
且回复写明"那不是本次采集的结果"；回放被明确标成回放且不计入"上次成功"。
不成立的也写清了：教师样例与模型课基线没有，界面还没在真浏览器点过，
真机遮挡也没实测。
