## 五、超时分支（服务器主动判定并留证）

超时不是"查的时候顺手算"，而是服务器后台看门狗**每秒扫一次并落库**，
所以超时这件事有服务器侧的时间戳。

实测（`tools/cmd_selftest.py --timeout-test`，发指令后故意不去取）：

```
request_id : CMD-20260918-0004
status     : timeout
created_at : 2026-09-18 10:51:42.258
timeout    : 2026-09-18 10:52:12.712（阶段=accept）
total_ms   : 30454
```

`timeout_stage` 区分两种完全不同的故障，验收时能一眼看出问题出在哪一段：

- **`accept`** —— 指令发出去了，板子一直没来取 → 板子掉线 / 重启 / 没在 上报
- **`exec`** —— 板子取走了，但没执行完 → 执行中崩了 / 上报通道断了

### 7.1 暂停周期上报（任务卡「后2学时」与「当堂验证」两处都要求）

任务卡原话要求**暂停周期上报、保持命令通道**，然后点采集、核对新观测与 `request_id`。
**这一条之前完全没做。**

难点在于：板子只做 POST、不监听端口，指令全靠搭在它**自己上报请求的响应体**里下发 ——
上报一停，通道就断了。任务卡那句"保持命令通道"正是指这个矛盾。

**解法**：暂停期间把「上报数据」换成「心跳」。

| 状态 | 板子发的请求 | 写库 | 取指令 |
|---|---|---|---|
| 正常 | `POST /api/data` | ✅ 写一条记录 | ✅ |
| 已暂停 | `POST /api/poll` | ❌ 一条都不写 | ✅ |

通道不断，而库里一条新传感记录都不会有。实测（`tools/pause_acceptance.py`，全自动）：

| 步骤 | 实测结果 |
|---|---|
| ① 基线 | 3 秒内库内 33783 → 33785（**+2**）—— 周期上报正常，作为对照 |
| ② 下发 `pause` | `CMD-20260923-0017` → `done`，四段 419 / 1459 / 884 ms，端到端 2762 ms |
| ③ 暂停生效（观察 6 秒） | 库内 33786 → 33786（**+0**）；板子自报 `paused=True`，**2.01 秒前刚发过心跳** |
| ④ 暂停中点采集 | `CMD-20260923-0018` → `done`，新采集 8 条，端到端 7220 ms |
| ⑤ **关键断言** | 这 8 条 **100% 是 `trigger='command'`，0 条 `timer`** |
| ⑥ 下发 `resume` | `CMD-20260923-0019` → `done`，3 秒内恢复 +2 条 |

第 ⑤ 步就是任务卡要的那个证明：**周期上报停着的时候，数据库里任何新记录都不可能来自
"页面翻出来的旧值"**。这比在界面上比数字硬得多。

> 附带修掉一个会造成"冤假错案"的隐患：暂停期间读数不再增长，数据年龄必然变大。
> 原来的逻辑只看年龄，会把它显示成「未更新 · 已 N 秒」—— 既冤枉了设备，
> 又**掩盖了"暂停生效"这个事实**。现在三态分开显示：
> 暂停中（心跳 N 秒前）/ 正在恢复 / 真未更新。

### 7.2 失败态：从死代码变成可复现的真实路径

任务卡要求 Web 显示「完成、**失败**或超时」。此前 `failed` 这个状态在状态机里定义了、
网页也能渲染，但**没有任何代码会设置它** —— 是死代码。

**为什么一直没验**：失败在真实环境里很难复现。拔网线的话，设备连"我失败了"都报不上来；
把服务器弄挂，整个链路一起断，分不清是谁的问题。

**做法**：给服务器加一个**受限的故障注入口**（`--fault-injection` 才生效，默认关闭），
让接下来 N 次「指令采集上报」返回 503。关键在于它**只拦样本、不拦回执**：

```
设备 → 样本上报 ×N   ← 被注入的故障挡住（503）
设备 → received 回执  ← 照常送达
设备 → failed 回执    ← 照常送达，带上原因
```

回执信道不被切断，测试才有确定的终点，而不是一路等到超时。

真机实测（`tools/fail_acceptance.py`，板子是真板子）：

| 步骤 | 实测结果 |
|---|---|
| 注入故障 | 接下来 6 条指令采集上报返回 503 |
| 下发采集 | `CMD-20260923-0008`：`issued`(0.0s) → `delivered`(0.8s) → `received`(2.4s) → **`failed`(11.1s)** |
| 设备备注 | **「6 条全部上报失败（网络或服务器不可达）」** |
| 库内核对 | 该 `request_id` 只有 **2 条**记录：1 条 `received` + 1 条 `failed`，**样本 0 条** |
| `timeout_ms` | `None` —— 是失败不是超时，两者落在不同的列 |
| **对照实验** | 撤掉故障后重采：`CMD-20260923-0009` → `done`，新采集 6 条，端到端 10587 ms |

最后那行对照是刻意加的：**没有它，就没法排除"板子本来就有病"这个解释。**
同一块板子、同一条链路，注入故障就失败、撤掉就成功 —— `failed` 这条路径因此是可信的。

补上失败态后还发现两处措辞/统计上的问题，一并修掉：

- 时间线第 4 步原先叫「执行完成」，失败时会显示成「**执行完成 · 执行失败（设备回报）**」，
  自相矛盾。改名为「**④ 执行结果**」—— 这一步本来就有三种结局。
- `failed` 的指令在接口里没有总耗时（`total_ms` 只算了 `done` 和 `timeout`），
  看起来像半条记录。已把 `failed_ms` 纳入。

#### 7.2.1 过程中发现的一个真问题：重复的终态回执

第一次真机验证时，库里出现了 **3 条一模一样的 `failed` 记录**（`seq` 60 / 61 / 62）。
查下来是：

- 服务器已经入库并返回 200，
- 但板子那边 `esp_http_client_fetch_headers()` 超时判为失败（板子自己的串口日志记了
  `上报失败 HTTP -1`），
- 于是板子按设计**重试**了结论上报 —— 而服务器每次都老老实实又插了一条。

上报是「发出去」和「收到回应」两件事，中间断了设备就分不清服务器处理没处理
（经典的两将军问题）。所以**设备必须重试，而服务器必须对重试免疫**。

修法：同一 `request_id` + 同一终态 `cmd_state` 已存在时，返回
`{"ok":true,"duplicate":true}` 且**不再入库**。判定很窄，只覆盖 `done` / `failed` ——
终态在状态机里本来就冻结了，第二条不携带任何新信息。

> 这类 bug 的产物是「看起来像证据、其实是错的数字」：`sample_count` 会变成 3，
> 页面显示成「本次新采集入库 4 条」。本项目在实体按键的事件 id 上已经栽过一次同样的坑，
> 这是第二次 —— 两次的共同点是：**重复/冲突的标识符被当成了新事实**。

### 7.3 重复点击（任务卡要求「测试重复点击」）

**策略：同一台设备的同类指令，同一时刻只允许一条在途。** 有在途的就返回 **409**，
并带上那条指令的 `request_id`。

为什么必须这样：连点 5 次若照单全收，服务器会排队 5 条，而设备 1 秒只能取走 1 条 ——
最后一条要在几十秒后才执行（那时用户早走开了），前面几条还会撞上 `accept` 超时，
页面上呈现出一片「完成 / 超时」混杂，看起来像 bug。

实测（`tools/dup_click_test.py`，**5 个请求并发发出**，模拟两个标签页/多台手机一起点）：

| 检查项 | 结果 |
|---|---|
| 受理 / 拒绝 | **恰好 1 条 202、4 条 409** |
| 拒绝指向哪条 | 4 条**都指向同一条**在途指令（不是各说各话） |
| 落盘核对 | 库里在途的 `recollect` **恰好 1 条** —— 没有偷偷排队 |
| 异类指令 | 采集在途时点「暂停」→ **202 放行**（不同类互不阻塞） |
| 闸门释放 | 在途那条走完后再点 → **202 受理** |
| 浏览器侧 | 在页面上下文里并发发两个请求 → **1 个 202 + 1 个 409** |

两个设计取舍值得写下来：

- **闸门按「同类」判定，不按设备全局判定。** 把暂停一起堵住会很难解释，也会挡住该做的事。
- **闸门必须在服务器。** 界面上的按钮 `disabled` 只能管住自己那个标签页，
  拦不住"两个浏览器同时点" —— 这正是浏览器侧那条检查存在的意义。
- **网页收到 409 不弹红字了事**，而是直接接到那条在途指令上继续跟踪。
  用户真正在意的不是"被拒绝了"，而是"我这一下到底有没有生效"。

## 八、复现方式

```bash
# 1) 启动服务器
python week1/server/server.py

# 2) 真机验收（下发指令 + 打印完整证据链）
cd week1
python tools/cmd_acceptance.py --samples 12 --interval-ms 100 --save

# 3) 无硬件时的服务器自测（软件模拟板子，含超时分支）
python tools/cmd_selftest.py --timeout-test

# 4) 网页操作：浏览器打开 http://127.0.0.1:8000
#    点「重新采集」→ 上方时间线会依次点亮四个阶段，
#    底部显示「下发前 N 条 → 下发后 M 条」，
#    表格里带「指令」标记的行就是本次新采的

# 5) 真实浏览器自动实测（自动点击按钮 + 截图）
python tools/browser_test.py

# 6) 暂停周期上报验收（会真的暂停/恢复真板子）
python tools/pause_acceptance.py

# 7) 重复点击 / 失败态（服务器级，不用硬件；跑完自动清理测试数据）
python tools/dup_click_test.py --clicks 5

# 8) 失败路径真机验收 —— 需要服务器带注入口启动
python week1/server/server.py --fault-injection      # 换这个方式起
python tools/fail_acceptance.py --samples 6 --interval-ms 120 --save

# 9) 网页能否显示「失败」的真实浏览器实测（同样需要 --fault-injection）
python tools/browser_test_fail.py
```

> `--fault-injection` 是一个**测试专用**开关：打开后可用
> `POST /api/debug/fault` 人为让设备上报失败，用于验证 `failed` 这条路径。
> 默认关闭，且启动横幅会明确打印「⚠️ 故障注入已开启」——
> 能人为制造故障的开关，忘了关必须一眼看得见。
