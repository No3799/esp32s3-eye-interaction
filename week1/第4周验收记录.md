### 2.1 一个必须记下来的环境坑

Ollama 0.40.3 的**托盘程序**启动服务时，读到的模型目录是
`C:\Users\user\.ollama\models`（指向 `D:\ollama\models` 的 junction）。
在这个 junction 路径下它解析不到模型清单：

```
level=WARN source=manifest.go:1628 msg="bad manifest"
  name=registry.ollama.ai/library/qwen3.8-q2:latest
  error="The system cannot find the path specified."
```

表现是 `/api/tags` 返回 `{"models":[]}`，`ollama list` 全空 —— 但 blob 和
manifest 明明都在 D 盘。用**显式** `OLLAMA_MODELS=D:\ollama\models` 启动就正常，
4 个模型全部可见。

处置：加了 `week1/启动语言服务.bat`（先 kill 托盘进程，再用显式路径起服务）。
这个坑值得单独记，因为它的表现是"助手全部意图解析失败"，
很容易被误判成"助手写错了"，而实际上语言服务压根没加载到模型。

### 3.3 「无完成证据不许说成功」专项

工具：`week1/tools/nl_timeout_test.py`

真服务器对离线设备下发指令 `CMD-20261023-0013`，不接任何板子：

```
[2] 直接下发指令: HTTP 202 → CMD-20261023-0013 status=issued
    指令最终状态: status=timeout timeout_stage=accept
[5] 数据库证据: id=CMD-20261023-0013 status=timeout timeout_stage=accept
    从受理到判定超时: 30.5 秒
```

三种无证据状态下的回答（逐一检查，均无成功声明）：

```
--- 状态 timeout ---
采集**超时**，没有完成证据。
- 状态：timeout（卡在 accept 阶段）
- 含义：设备一直没来取这条指令（掉线或重启），**不能据此判定硬件坏了**。

--- 状态 failed ---
采集**失败**：设备回报了失败，没有完成证据。
- 状态：failed
- 设备备注：设备回报失败

--- 状态 issued ---
采集请求已下发，但**还没有完成证据**（当前状态 issued）。
```

闸门单元检查：

```
拦截结果: ok=False 原因=无完成证据却声称「已采集成功」   ← 无证据时拦下
有证据时: ok=True  原因=（无）                          ← 有证据时放行
```

### 3.4 备用路径（语言服务故障）

这一项不是"故意造一个故障来演示"，而是**真的撞上了一次**，所以证据分两部分：
真实故障的现场记录，以及故障暴露出来后补的那一层分类。

#### 3.4.1 现场：2026-10-28 10:11，语言服务确实挂了

那天上午助手对所有提问都回同一句话：

```
ok: False | error: llm_unavailable
语言模型服务暂时不可用，我没法判断这句话的意图，所以没有执行任何采集动作。
trace: {'step': 'intent_parse', 'ok': False, 'error': 'HTTP Error 404: Not Found'}
```

查下去是 **Ollama 托盘程序启动的服务读不到模型清单**：

```
/api/tags        → {"models":[]}            ← 模型"消失"了
server.log       → bad manifest ... The system cannot find the path specified.
D:\ollama\models → 模型文件、manifest、blob 全都在（27GB）
```

用**显式**模型目录另起一个实例（`OLLAMA_MODELS=D:\ollama\models`）后，
同一个目录立刻列出 4 个模型 —— 所以不是数据坏了，是启动方式的问题。
处理办法写进了 `week1/启动语言服务.bat`。

**这次故障顺带证明了「不执行动作」不是嘴上说说**，数据库可查：

| 检查 | 结果 |
|---|---|
| 故障窗口 10:10–10:12 下发过的指令 | **0 条**（`commands` 表按 `created_ms` 查） |
| 同期设备 1Hz 定时上报 | **94 条**，一条没断 |
| 结论 | 坏的只是"语言→意图"这一层；**采集链路没被牵连，也没有任何误下发** |

#### 3.4.2 故障暴露的缺陷：四种失败被压成了一句"服务不可用"

原来的降级分支只输出 `llm_unavailable` + 一份**占位符 schema**。这有两个问题：

1. **分不清该修什么**。"模型没加载"（404）和"模型输出不是 JSON"是两回事，
   前者要重启服务，后者要改提示词。混成一句，人会去重启一个本来正常的服务。
2. **给的是 schema 不是样例**。`"intent": "query_latest|request_recollect|…"`
   只能说明字段名，没法拿去和模型的实际输出逐字段比对。

改成四类 + 具体实例：

| `error_kind` | 含义 | 该修什么 |
|---|---|---|
| `model_not_found` | 服务在跑，模型没加载 / 名字不对 | 查 `/api/tags`，用启动脚本重启 |
| `model_unreachable` | 服务没起 / 端口不通 / 超时 | 起服务、查端口 |
| `model_auth` | 连上了但拒绝授权 | 换 `NL_LLM_API_KEY` |
| `invalid_json` | 服务正常，模型输出不合法 | 收窄提示词 / 换更稳的模型 |

返回体同时加了两个**机器可读**字段：

```json
{
  "ok": false,
  "error": "llm_unavailable",
  "error_kind": "model_not_found",
  "actions_taken": [],
  "parse_sample": {
    "intent": "unclear", "device_id": "", "samples": null,
    "interval_ms": null, "reason": "模型侧失败（model_not_found），未解析出意图"
  }
}
```

`actions_taken: []` 是给验收用的：**"什么都没做"从此可以断言，而不用读自然语言**。
`parse_sample` 是具体实例，不是 `a|b|c` 这种占位符。

#### 3.4.3 判据以异常类型为主，文本只作兜底（这一条是踩出来的）

第一版用英文关键词匹配（`refused` / `timed out`）判"端口不通"。
**用真实故障注入一测就挂了**：中文 Windows 抛的是

```
URLError(ConnectionRefusedError(10061, '由于目标计算机积极拒绝，无法连接。'))
```

文本里没有 `refused`，于是被归成 `model_error`。
改成按 `HTTPError.code` 和 `URLError.reason` 的**类型**判断，文本只兜底。

自检工具：`week1/tools/test_llm_fallback.py`（20 项，含两次真实故障注入）

```
=== A. 四种失败是否被分开归类 ===   （4 × 4 项断言）
=== B. 真实故障注入 ===
  真·模型不存在 → model_not_found      ← 真的去请求一个不存在的模型
  真·端口不通   → model_unreachable    ← 真的去连一个没人监听的端口
=== C. 一次真实失败的人话输出 ===
结果：全部通过
```

## 四、真实浏览器实测

工具：`week1/tools/browser_test_nl.py`（Chrome 无头 + DevTools Protocol）
截图：`week1/debug_logs/week4_nl_panel.png`

**为什么不能只做静态检查**：用 JS 的 `.click()` 点一个隐藏元素照样生效，
于是"按钮其实点不到"会被测成通过 —— 这是个假通过。
所以这里用 `Input.dispatchMouseEvent` 发**真鼠标事件**，
并且点击前先量可见性（`getBoundingClientRect` 有尺寸、`offsetParent` 不为空）。

```
✓ 语言标签存在          ✓ 回答含数值              ✓ 真鼠标点击「重新采集一次」
```

## 五、为什么这样分工（设计取舍）

### 5.1 模型只出参数，不出结论

如果让模型直接生成答案，它一定会把话说圆。实测过一次：
问"查看上次数据"，模型在 JSON 里给了正确的 `intent`，
但如果在提示词里放开让它写答案，它就会补上"数据正常"这类它无权判断的话。

所以分工是硬的：**模型输出被当成参数，不被当成结论**。
回答里的数值、时间、状态全部由服务端从工具返回值填。

### 5.2 两种"没有证据"必须分开说

- `timeout` + `accept` 阶段 = 设备一直没来取指令（掉线/重启）
- `timeout` + `exec` 阶段 = 取了但没执行完

这两种故障的排查方向完全不同（前者查网络/电源，后者查固件/传感器），
所以第2周就分了 `timeout_stage`，本周的回答里也照实说"卡在哪个阶段"。
并且明确写「**不能据此判定硬件坏了**」—— 超时不等于硬件故障。

### 5.3 设备范围按活跃度分，不按"库里有没有"

见 `docs/design/13` 第 3.2 节。简单说：库里有一台第1周模拟器 `selftest-sim`，
如果按"出现过的所有设备"算范围，用户只有一台真板子却要被要求"指明设备"。
所以：未指明时只看活跃设备，点名时可以查历史设备。
