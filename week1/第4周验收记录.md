### 2.1 一个必须记下来的环境坑

Ollama 0.40.3 的**托盘程序**启动服务时，读到的模型目录是
`C:\Users\user\.ollama\models`（指向 `D:\ollama\models` 的 junction）。
在这个 junction 路径下它解析不到模型清单：

```
level=WARN source=manifest.go:1628 msg="bad manifest"
  name=registry.ollama.ai/library/qwen3.8-q2:latest
  error="The system cannot find the path specified."
```

表现是 `/api/tags` 返回 `{"models":[]}`，`ollama list` 全空 —— 但 blob 和
manifest 明明都在 D 盘。用**显式** `OLLAMA_MODELS=D:\ollama\models` 启动就正常，
4 个模型全部可见。

处置：加了 `week1/启动语言服务.bat`（先 kill 托盘进程，再用显式路径起服务）。
这个坑值得单独记，因为它的表现是"助手全部意图解析失败"，
很容易被误判成"助手写错了"，而实际上语言服务压根没加载到模型。

### 3.3 「无完成证据不许说成功」专项

工具：`week1/tools/nl_timeout_test.py`

真服务器对离线设备下发指令 `CMD-20261023-0013`，不接任何板子：

```
[2] 直接下发指令: HTTP 202 → CMD-20261023-0013 status=issued
    指令最终状态: status=timeout timeout_stage=accept
[5] 数据库证据: id=CMD-20261023-0013 status=timeout timeout_stage=accept
    从受理到判定超时: 30.5 秒
```

三种无证据状态下的回答（逐一检查，均无成功声明）：

```
--- 状态 timeout ---
采集**超时**，没有完成证据。
- 状态：timeout（卡在 accept 阶段）
- 含义：设备一直没来取这条指令（掉线或重启），**不能据此判定硬件坏了**。

--- 状态 failed ---
采集**失败**：设备回报了失败，没有完成证据。
- 状态：failed
- 设备备注：设备回报失败

--- 状态 issued ---
采集请求已下发，但**还没有完成证据**（当前状态 issued）。
```

闸门单元检查：

```
拦截结果: ok=False 原因=无完成证据却声称「已采集成功」   ← 无证据时拦下
有证据时: ok=True  原因=（无）                          ← 有证据时放行
```

## 五、为什么这样分工（设计取舍）

### 5.1 模型只出参数，不出结论

如果让模型直接生成答案，它一定会把话说圆。实测过一次：
问"查看上次数据"，模型在 JSON 里给了正确的 `intent`，
但如果在提示词里放开让它写答案，它就会补上"数据正常"这类它无权判断的话。

所以分工是硬的：**模型输出被当成参数，不被当成结论**。
回答里的数值、时间、状态全部由服务端从工具返回值填。

### 5.2 两种"没有证据"必须分开说

- `timeout` + `accept` 阶段 = 设备一直没来取指令（掉线/重启）
- `timeout` + `exec` 阶段 = 取了但没执行完

这两种故障的排查方向完全不同（前者查网络/电源，后者查固件/传感器），
所以第2周就分了 `timeout_stage`，本周的回答里也照实说"卡在哪个阶段"。
并且明确写「**不能据此判定硬件坏了**」—— 超时不等于硬件故障。

### 5.3 设备范围按活跃度分，不按"库里有没有"

见 `docs/design/13` 第 3.2 节。简单说：库里有一台第1周模拟器 `selftest-sim`，
如果按"出现过的所有设备"算范围，用户只有一台真板子却要被要求"指明设备"。
所以：未指明时只看活跃设备，点名时可以查历史设备。
