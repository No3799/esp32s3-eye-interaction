## 一、这一周要证明什么

一句话：**语音只是给已有入口换了个"输入方式"和"输出方式"，不是新的一条业务链路。**

这条如果成立，那么：
- 语音问「查看上次数据」和打字问，**必须得到同一个回答结构**（同样的来源/时间/状态）
- 语音链路上的任何故障，都**不能**影响文字入口
- 板子能听、不能说的这个事实，必须在界面上写清楚，不能让人误以为"板子会讲话"

## 二、链路与运行位置

```
        ┌──────────── 板子（ESP32-S3-EYE）────────────┐
按下   │ BOOT 键 → I2S 采 16k/16bit/单声道             │
BOOT   │        → PSRAM 缓冲（最长 10 秒）              │
       │        → 封 44 字节 WAV 头                    │
       └──────────────────┬───────────────────────────┘
                          │ POST /api/audio（160KB 左右）
       ┌──────────────────▼───────────────────────────┐
       │ 服务器：存一份 → 调 worker 识别                │
       │   asr_worker.py（vosk 中文小模型，本机离线）    │
       └──────────────────┬───────────────────────────┘
                          │ {"ok":true,"text":"查看上次数据"}
       ┌──────────────────▼───────────────────────────┐
       │ 浏览器：识别出的文字 → **第4周同一个 /api/ask** │
       │        → 受限工具 → 真实结果                  │
       │        → speechSynthesis 播报（电脑出声）      │
       └──────────────────────────────────────────────┘
```

**运行位置**（任务卡点名）：采集在**板子**、识别在**电脑（本机离线）**、执行在**服务器+板子**、
播报在**电脑**。板子没有扬声器，**不会出声**。

## 三、五条错误路径的实测

工具：`week1/tools/test_asr_paths.py`（**10 项全过**）

```
① 无声         全部零 PCM       → silence           HTTP 200
② 有声音没词   440Hz 提示音     → empty_text        HTTP 200
③ 不是 WAV     随便一段字节      → audio_unreadable  HTTP 400
④ 超过 4MB     4MB+             → too_large         HTTP 413
⑤ 服务超时     阈值压到 0.05 秒  → asr_timeout       HTTP 504（耗时 0.06 秒）
```

**为什么超时那条要另起一个实例**：正常识别只要 0.5~1 秒，阈值 30 秒永远碰不到。
不把阈值压到不合理的小值，这条路径一次也跑不到 —— 而它恰恰是"服务挂了用户会看到什么"的唯一证据。

### 这个测试逼出来的两个真 bug

**bug 1：超长录音时，客户端读不到那句提示。**
服务端超过 4MB 直接回 413 然后关连接，而客户端还在写剩下的字节 ——
Windows 上收到 RST，于是那句"录音太长了"根本传不到浏览器，页面只会显示 "Failed to fetch"。
修法：`_drain_body()` 先把请求体排空（带上限）再回错误。

**bug 2：DNS 不稳时服务启动卡死。**
`HTTPServer.server_bind()` 里有一句 `socket.getfqdn(host)` 会做反向 DNS 解析。
这台机器 DNS 不稳，于是进程停在启动第一行：**端口已 bind 但从不 listen、日志 0 字节**，
看起来像"服务根本没启动"。修法：子类化只做真正的 bind，启动不依赖 DNS。

## 五、真实语音：从"做不到"到"跑通了"

这条曾经卡了三层，现在前两层已解决、第三层已完成：

1. **这台电脑没有麦克风** —— `getUserMedia` 抛 `NotFoundError`；系统里
   `麦克风-Rear (3- Senary Audio)` 状态是 **Unknown（未连接）**，粉色插孔是空的。
   （用浏览器假麦克风只能验证"除词汇准确率以外的全部链路"，测不出"听没听对"。）
2. **改用板载麦克风解决** —— 板上是 MSM261S4030H0R（I2S，SCK=41/WS=42/SD=2），
   自写 I2S 采集固件 + `/api/audio` 接收 + BOOT 键控制起停。
3. **真人开口已完成**：2026-10-29 13:55:17，操作者按 BOOT 说了「你好」，
   板子录到 **105,004 字节（≈3.3 秒，未截断）**，识别为「你好」，
   走第4周入口判定 `intent=unclear`，回答是收敛的追问句 —— **没有瞎执行任何动作**。

这条实测同时验证了三件容易忽略的事：

| 观察 | 为什么重要 |
|---|---|
| 3.3 秒的音频只有 105KB | 与"16k/16bit 单声道 = 32KB/秒"对得上，采样格式没跑偏 |
| `truncated=false` | 10 秒上限没被触发，长度够用 |
| 说完「你好」得到的是追问，不是"已采集成功" | 无依据时不编结果，这是第4周立下的规矩在语音入口同样生效 |

**播报这一环：不是没实现，是没有喇叭。**

这台机器没有任何可听的音频输出设备，所以"人耳能不能听到"在这里无法验证。
但"接了 API"和"引擎真的在跑"是两件事，不能混着说。`tools/check_tts.py` 在真 Chrome 里
念一句中文并收集事件：

```
可用语音  zh-CN / Microsoft Huihui
事件序列  start → boundary ×9 → end      全程 4.27 秒，无 onerror
```

`boundary` 是**音频推进到某个词边界**才会触发的事件 —— 连续 9 次说明音频真的在播放，
不是只调了个空 API。所以结论是：

| 说法 | 是否成立 |
|---|---|
| 播报链路已接通、引擎能合成并输出 | ✅ 有事件证据 |
| 这台电脑能听到播报 | ❌ 没有扬声器，无法验证（环境限制） |

要真正"听到"，插一个耳机或 USB 音箱即可，代码不用改。

| 1 | 开始录音借用的是"检测到按键"那一下短亮 —— 与按 MENU 求助**一模一样** | 开始改成 **短亮 → 常亮**：灯亮着＝正在录 |
| 2 | 结束录音**没有任何灯效**，直接黑着 | 结束改成 **灭 → 短闪 2 次 → 灭**：灯灭了＝录完了 |
| 3 | 录满 10 秒采集任务自己停了，**主逻辑不知道**；此时再按 BOOT 会重新开一段，**上一段直接丢** | 新增 `mic_take_auto_stop()`：录满自动结束并上传 |

第 1、2 条的设计要点是**用稳态而不是节奏**：站在板子边上的人不必数闪几下，
只要看"灯亮着没有"。开始与结束互为镜像（暗→常亮 / 常亮→暗）。

第 3 条是这轮最严重的一个：它不表现为"灯不对"，而表现为**数据静默丢失** ——
录满 10 秒后按 BOOT 看起来像正常结束，实际上一段音频从没上传过。

另外加了 `s_led_hold`：录音期间按四个求助键时，灯效会插进来并以"灭"收尾，
不补回来的话"亮着=正在录"就被打断了。现在任何别的灯效播完都会自动补亮，
只有 `REC_STOP` 允许它灭。

灯效语义已同步到 [`docs/design/09`](../docs/design/09-实体按键与本地反馈.md) 的对照表与网页说明。

### 8.1 录音上限 5 秒 → 10 秒

5 秒对"查看上次数据"这类短指令够用，但一句话稍长就被切断；**而切断在听感上没有提示**，
只会表现为"识别不准"——人会一遍遍重说，不会想到是长度限制。

改成 10 秒的依据（都不是估算，是现成的数）：

| 约束 | 实际情况 |
|---|---|
| 内存 | 320KB × 2 = 640KB；PSRAM 空闲 **7.84MB**（占 8%） |
| 上传 | 320KB 走 WiFi 约 1~3 秒；`/api/audio` 的 HTTP 超时 **15 秒** |
| 识别 | vosk 小模型约 0.5~1 倍实时 → 3~8 秒；ASR 超时 **30 秒** |
| 服务端上限 | `/api/audio` 收 1MB，10 秒音频 320KB，仍有一倍余量 |

不做到 30 秒的理由：1.9MB 内存、近 1MB 上传，而**上传期间 1Hz 上报是停着的**
（HTTP 客户端只允许主循环一个使用者）。

配套补了一件事：**截断要报出来**。板子上传时带 `?truncated=1`，服务端存进记录，
页面显示「录音被截断（10 秒上限）」。不这样的话，"被切成半句"和"模型听错"
在页面上完全一样，责任会被记到识别头上。

## 九、选定的语音任务（#17）与它的边界

**任务**：不用打开电脑网页，对着板子说一句「重新采集一次」就触发一次采集。

**为什么它有操作价值**：它替换掉的是一串真实动作 ——
打开电脑 → 打开网页 → 找到采集按钮 → 点一下。语音省掉的是**这四步**，
不是省掉采集本身。手上拿着板子、手脏、或者人不在电脑旁边时，这四步就是阻力。

### 但"在外面"这个说法要打个折，写清楚才经得起问

| 边界 | 现在成立到什么程度 |
|---|---|
| **网络** | 语音链路是「板子 → 局域网服务器（10.1.41.18）」。**离开这个 WiFi 就不成立** —— 公网部署在第 3 周已决定不做。所以"在外面"目前指**同一 WiFi 覆盖内**（实验室、家里走动），不是"远离这台电脑" |
| **播报** | 板子没有扬声器，这台电脑也没有可听的输出设备。真正在"外面"时**听不到回答**，"采到了"只能靠灯（连闪 2 下） |
| **采集本身** | 语音只是触发方式。"完成"仍要两项同时成立：指令回执 `done` **且** 库里有带同一 `request_id` 的新记录（第 4 周的规矩不变，见 `design/13`） |

**要不要补第一边界**：补公网就能真正"在外面"用，代价就是第 3 周欠下的 VPS 部署。
这是取舍，不是遗漏 —— 记录里如实标着，真要做的时候单独开一轮。

### 怎么验证这条任务

按 BOOT → 说「重新采集一次」→ 再按 BOOT。预期：

1. 灯：短亮→常亮（在录）→ 灭+闪两下（录完）→ 连闪 2 下（上传成功）
2. `/api/audio/latest` 出现一条 `intent=request_recollect`、`tool=request_recollect`
3. 回答里写明「指令回执 + 新观测入库，两项证据齐全」，并给出 `request_id` 与新记录条数

---

**一句话结论**：语音链路**真机跑通了** —— 板载麦克风录到的「查看上次数据」被正确识别，
走完第4周那条入口并读到真实记录；同一句用文字问，两条路的回答**结构完全一致**；
播报引擎实跑 4.27 秒（本机无扬声器，只有"人耳听到"这一层验不了）。
工程侧的薄弱环节（错误路径、截断、四状态）都有可重复的验证。

剩下的 3 项都不是工程问题：#10 端侧课接口由本项目自行替代（⚠️），
#8 教师验证、#19 共享音频站补验需要外部条件（❌）。

#17 已选定为「免开网页、对板子说一句就采一次」，但它"在外面"的适用范围受限于
局域网与无扬声器 —— 边界写在第九节，不藏。
