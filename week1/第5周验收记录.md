## 一、这一周要证明什么

一句话：**语音只是给已有入口换了个"输入方式"和"输出方式"，不是新的一条业务链路。**

这条如果成立，那么：
- 语音问「查看上次数据」和打字问，**必须得到同一个回答结构**（同样的来源/时间/状态）
- 语音链路上的任何故障，都**不能**影响文字入口
- 板子能听、不能说的这个事实，必须在界面上写清楚，不能让人误以为"板子会讲话"

## 二、链路与运行位置

```
        ┌──────────── 板子（ESP32-S3-EYE）────────────┐
按下   │ BOOT 键 → I2S 采 16k/16bit/单声道             │
BOOT   │        → PSRAM 缓冲（最长 10 秒）              │
       │        → 封 44 字节 WAV 头                    │
       └──────────────────┬───────────────────────────┘
                          │ POST /api/audio（160KB 左右）
       ┌──────────────────▼───────────────────────────┐
       │ 服务器：存一份 → 调 worker 识别                │
       │   asr_worker.py（vosk 中文小模型，本机离线）    │
       └──────────────────┬───────────────────────────┘
                          │ {"ok":true,"text":"查看上次数据"}
       ┌──────────────────▼───────────────────────────┐
       │ 浏览器：识别出的文字 → **第4周同一个 /api/ask** │
       │        → 受限工具 → 真实结果                  │
       │        → speechSynthesis 播报（电脑出声）      │
       └──────────────────────────────────────────────┘
```

**运行位置**（任务卡点名）：采集在**板子**、识别在**电脑（本机离线）**、执行在**服务器+板子**、
播报在**电脑**。板子没有扬声器，**不会出声**。

## 三、四条错误路径的实测

工具：`week1/tools/test_asr_paths.py`（**10 项全过**）

```
① 无声         全部零 PCM       → silence           HTTP 200
② 有声音没词   440Hz 提示音     → empty_text        HTTP 200
③ 不是 WAV     随便一段字节      → audio_unreadable  HTTP 400
④ 超过 4MB     4MB+             → too_large         HTTP 413
⑤ 服务超时     阈值压到 0.05 秒  → asr_timeout       HTTP 504（耗时 0.06 秒）
```

**为什么超时那条要另起一个实例**：正常识别只要 0.5~1 秒，阈值 30 秒永远碰不到。
不把阈值压到不合理的小值，这条路径一次也跑不到 —— 而它恰恰是"服务挂了用户会看到什么"的唯一证据。

### 这个测试逼出来的两个真 bug

**bug 1：超长录音时，客户端读不到那句提示。**
服务端超过 4MB 直接回 413 然后关连接，而客户端还在写剩下的字节 ——
Windows 上收到 RST，于是那句"录音太长了"根本传不到浏览器，页面只会显示 "Failed to fetch"。
修法：`_drain_body()` 先把请求体排空（带上限）再回错误。

**bug 2：DNS 不稳时服务启动卡死。**
`HTTPServer.server_bind()` 里有一句 `socket.getfqdn(host)` 会做反向 DNS 解析。
这台机器 DNS 不稳，于是进程停在启动第一行：**端口已 bind 但从不 listen、日志 0 字节**，
看起来像"服务根本没启动"。修法：子类化只做真正的 bind，启动不依赖 DNS。

## 五、为什么"真实语音"这一条还没打勾

三层原因，从外到内：

1. **这台电脑没有麦克风**。`getUserMedia` 抛 `NotFoundError`；系统里
   `麦克风-Rear (3- Senary Audio)` 状态是 **Unknown（未连接）**，粉色插孔是空的。
2. **所以改用板载麦克风**。板上有 MSM261S4030H0R（I2S，SCK=41/WS=42/SD=2），
   固件已写好并烧录，服务端 `/api/audio` 用提示音测过能收能识别。
3. **但"真人对着板子说一句"这一步没人做**。假麦克风给的是提示音、TTS 合成音也不是人声，
   而"词汇准确率"只能靠真人。**这一条我不替它打勾。**

## 八、2026-10-29 补充修正（操作者反馈驱动）

操作者按了 BOOT 之后提出：**看不出这次按键是"开始录音"还是"结束录音"**。查下去是三个问题：

| # | 问题 | 改法 |
|---|---|---|
| 1 | 开始录音借用的是"检测到按键"那一下短亮 —— 与按 MENU 求助**一模一样** | 开始改成 **短亮 → 常亮**：灯亮着＝正在录 |
| 2 | 结束录音**没有任何灯效**，直接黑着 | 结束改成 **灭 → 短闪 2 次 → 灭**：灯灭了＝录完了 |
| 3 | 录满 10 秒采集任务自己停了，**主逻辑不知道**；此时再按 BOOT 会重新开一段，**上一段直接丢** | 新增 `mic_take_auto_stop()`：录满自动结束并上传 |

第 1、2 条的设计要点是**用稳态而不是节奏**：站在板子边上的人不必数闪几下，
只要看"灯亮着没有"。开始与结束互为镜像（暗→常亮 / 常亮→暗）。

第 3 条是这轮最严重的一个：它不表现为"灯不对"，而表现为**数据静默丢失** ——
录满 10 秒后按 BOOT 看起来像正常结束，实际上一段音频从没上传过。

另外加了 `s_led_hold`：录音期间按四个求助键时，灯效会插进来并以"灭"收尾，
不补回来的话"亮着=正在录"就被打断了。现在任何别的灯效播完都会自动补亮，
只有 `REC_STOP` 允许它灭。

灯效语义已同步到 [`docs/design/09`](../docs/design/09-实体按键与本地反馈.md) 的对照表与网页说明。

### 8.1 录音上限 5 秒 → 10 秒

5 秒对"查看上次数据"这类短指令够用，但一句话稍长就被切断；**而切断在听感上没有提示**，
只会表现为"识别不准"——人会一遍遍重说，不会想到是长度限制。

改成 10 秒的依据（都不是估算，是现成的数）：

| 约束 | 实际情况 |
|---|---|
| 内存 | 320KB × 2 = 640KB；PSRAM 空闲 **7.84MB**（占 8%） |
| 上传 | 320KB 走 WiFi 约 1~3 秒；`/api/audio` 的 HTTP 超时 **15 秒** |
| 识别 | vosk 小模型约 0.5~1 倍实时 → 3~8 秒；ASR 超时 **30 秒** |
| 服务端上限 | `/api/audio` 收 1MB，10 秒音频 320KB，仍有一倍余量 |

不做到 30 秒的理由：1.9MB 内存、近 1MB 上传，而**上传期间 1Hz 上报是停着的**
（HTTP 客户端只允许主循环一个使用者）。

配套补了一件事：**截断要报出来**。板子上传时带 `?truncated=1`，服务端存进记录，
页面显示「录音被截断（10 秒上限）」。不这样的话，"被切成半句"和"模型听错"
在页面上完全一样，责任会被记到识别头上。
