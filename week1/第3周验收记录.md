## 三、真机证据链

### 3.1 修复后固件（2026-09-20 14:58，四次按键）

| 事件 id | 按键 | 新采集 | 记录 id | 入库跨度 | 按下→首条采样 |
|---|---|---|---|---|---|
| `BTN-2a3613-UP+-0001` | UP+ | **5 条** | 26153 ~ 26157 | 1608 ms | 471 ms |
| `BTN-2a3613-DN--0002` | DN− | **5 条** | 26160 ~ 26164 | 1115 ms | 1221 ms |
| `BTN-2a3613-MENU-0003` | MENU | **5 条** | 26167 ~ 26171 | 968 ms | 1061 ms |
| `BTN-2a3613-PLAY-0004` | PLAY | **5 条** | 26175 ~ 26179 | 893 ms | 691 ms |

四个键都识别正确、每次都恰好 5 条、跨度都在 1~2 秒内。

**「按下→首条采样」为什么是几百毫秒到 1 秒多？** 因为主循环正在等上一次
HTTP 上报的响应（超时上限 2 s），按键要等它回来才轮得到。
这个数字如实反映了当前架构的代价，见 `docs/design/09` 第 2.3 与第 6 节。

### 3.2 三种触发方式在同一条数据上可区分

```
库内总数 25213 条
  timer   : 4657 条   ← 板子自己 1Hz 上报
  command :   67 条   ← 网页点「重新采集」下发指令产生
  button  :   65 条   ← 板载实体按键产生
```

`trigger` / `request_id` / `button` 三个字段一起，让"这条数据是谁触发的"
成为**数据库里的直接关联**，而不是靠时间窗口猜。

### 3.3 一次按键与一次刷新的区别

| 动作 | 服务器行为 | 库内条数 | 新数据的标记 |
|---|---|---|---|
| 刷新网页 | 只读 SQLite | **不变** | — |
| 点「重新采集」 | 受理指令、等设备执行 | +5 ~ +13 | `trigger='command'` + `request_id='CMD-…'` |
| **按板上的键** | 设备**主动**上报 | **+5** | `trigger='button'` + `button='MENU'` |

注意第三行与前两行有个本质差别：**按键没有下行通道** —— 没有"服务器受理"
和"指令下发"两步。所以网页上给按键事件画四阶段时间线会是伪造证据，
面板里刻意只列真实发生的事。

## 六、过程中发现并修复的两个真问题

### 6.1 事件 id 跨重启重复，导致两次按键被合并（严重）

**现象**：第一次真机测试得到的事件，样本数 10、入库跨度 104839 ms —— 都不对。

```
BTN-UP+-0001   UP+  样本=10  id 25839~25941  跨度=107352 ms   ← 应该是 5 条 / 约 2 秒
```

**根因**：事件 id 用的是内存里的计数器 `s_btn_n`，**板子一重启就归零**。
两次不同时间按的 UP+ 生成了同一个 id，服务器按 id 聚合时把两次按合成了同一条。

**修复**：给事件 id 加**上电随机前缀**（24 位）：

```
修复前: BTN-UP+-0001
修复后: BTN-2a3613-UP+-0001      ← 2a3613 = esp_random() & 0xFFFFFF，每次上电不同
```

**为什么这件事值得单独记**：它产出的不是"没有数据"，而是**看起来像证据、
实际是错的**数据。样本数 10、跨度 105 秒，如果不去核对，会直接被写成
"一次按键采了 10 条、耗时 105 秒"。**错的证据比没有证据更危险。**

**顺带加的防线**：网页现在会把跨度 > 30 秒的事件标红提示
「跨度异常 · 事件 id 可能撞车」—— 让这类问题在界面上自己暴露，而不是靠人盯着数字发现。
修复前的 4 条旧事件仍保留在库里，正好当作这个告警的实物样本。

### 6.2 串口工具把板子复位了，导致 200 秒采集空白

**现象**：第一版 `btn_probe.py` 打开 COM5 后，200 秒里**一个字节都没收到**，
但板子其实活着（服务器一直在收数据）。

**根因**：pyserial 打开串口时默认拉高 DTR/RTS，而 ESP32-S3 上这两个信号的组合
会触发芯片复位。于是"打开串口"这个动作本身把板子重启了；芯片重启 → USB 重新枚举
→ Windows 下**旧句柄静默失效**（不报错，只是再也读不到数据）。

**修复**：打开后显式 `setDTR(False)` / `setRTS(False)`，并加一个看门狗 ——
连续 5 秒读不到数据就关掉重开串口。

**教训**：调试工具本身也会改变被测对象的状态。**"观测不到"要先怀疑观测手段，
再怀疑被测对象。**

## 十、断网实测（任务卡「当堂验证」第①句）

任务卡原文：

> **断开外网后，本地仍能确认按键已触发；无远端接收证据时不得显示"对方已收到"。**

这一句是两件事，两件都要证。工具：`tools/offline_test.py`（只取证，不替你下结论）。

### 10.1 这一句要证明什么

**求助最可能发生在没网的时候。** 如果本地反馈是"等服务器回话才亮灯"，
那断网时按下去就毫无反应 —— 这个功能会在最需要它的一刻失效。
所以要证明的是：**本地确认这条链路完全不经过网络**；
同时**不许谎报**：没有远端证据就不能显示"对方已收到"。

### 10.2 怎么做

停掉服务器（这台电脑只跟服务器通信，所以"够不到服务器"就等于对板子断网），
然后按一下板子上的键，看绿灯。

**不挂串口。** 本板 COM5 是 ESP32-S3 自带的 USB-Serial/JTAG，
重复开关端口会扰动芯片复位状态 —— 2026-09-23 就是串口工具把板子搞下线的，
不会为了一个测试再冒一次险。所以灯效**只能由人的眼睛确认**，
脚本不读串口、也不替你下这个结论。

### 10.3 第一次测试：**数据被污染，作废**

第一轮的服务器日志：

```
10:40:19  POST /api/help   201   ← 服务器活着
10:40:25  POST /api/help   201
10:40:28  POST /api/help   201
10:40:40  POST /api/help   201
10:40:47  POST /api/help   201   ← 服务器还活着
10:40:49  POST /api/data   200   ← 服务器最后一条
          ──── 之后 38.3 秒零记录 ────
```

**按键发生在服务器仍存活期间，5 次全部 201 入库。** 那几次板子收到的是"成功"，
灯应当是**连闪 2 次**而不是快闪 5 次 —— 也就是说"断网期间按了键"这个前提没被满足，
这一轮**不能作为断网证据**。

根因是流程：先取基线、再发停服命令、然后就问人按了没有。
而**停服要花几秒**（PowerShell 启动 + 结束进程），这几秒里服务器还活着，
按键就落在窗口外面了。基线快照与服务器真正离线之间必然有这一段空隙。

那 5 条误产生的"待回应"事件**保留在库里当历史**，只标记为已取消
（原因写的是"验收测试期间的按键，非真实求助"），没有删除。

### 10.4 第二次测试：先确认静默，再按

改成三步，把主动权握在手上：

1. 取基线；
2. 停服务器；
3. **轮询数据库，等它连续 4 秒零新增之后**，才告诉人去按键。

第 3 步是关键 —— 它把"服务器到底停了没"从**推断**变成**测量**。
实测输出：

```
起始 max_id = 54921
✓ 已连续 4 秒零新增（max_id 停在 54921）—— 静默窗口已打开
8000: 已释放
```

确认之后才请人按键。结果：

| 层 | 观察 | 来源 |
|---|---|---|
| ① 本地确认 | 绿灯**短亮一下** | 人的眼睛（板边现场） |
| ② VPS 接收 | **无**（服务器侧 0 条求助事件） | `offline_test.py` compare |
| ③ 查看者回应 | **无**（没有人点过按钮） | 界面 ③ 徽标不亮 |

`tools/offline_test.py` 的判读输出：

```
窗口总长 : 79.4 秒
[传感记录]   最长静默段 : 71.5 秒   10:42:48.100 → 10:43:59.573   期间 0 条记录
[求助事件]   整个窗口新增 : 0 条   其中落在静默段内 : 0 条
[下行指令]   整个窗口新增 : 0 条

✓ 窗口内存在 71.5 秒的零记录静默段 —— 服务器确实离线过
✓ 静默段内求助事件 0 条 —— 这期间任何按键都没有变成服务器上的一条记录
✓ 因此页面上不可能显示这次按键的 ②VPS接收 / ③查看者回应
```

**于是任务卡那句两句都成立**：
① 断网后本地仍确认（灯亮了）；② 没有远端证据就不显示"对方已收到"。

### 10.5 两项补充检查

**① 不补发。** 服务器恢复后，板子 0.0 秒内接上（`seq` 继续递增、RSSI −43），
但**没有**凭空多出一条迟到的求助 —— 最新的求助事件仍是 10:40:47 那条。
说明设备发不出去的消息就是丢了，不会在服务器恢复后突然冒出来。
（这也和固件的设计一致：求助消息**单次尝试、不缓存**。）

**② 断网期间板子没有"死"。** 服务器一恢复它就立刻上报，
说明它在整段静默里每秒都在重试 —— 静默的原因在服务器这一侧，不在板子。

### 10.6 顺带发现（未查明）

上一次更长的断网（2026-09-23，4.63 小时）之后，板子的 `device_ms` 从 110.5 秒
只涨到 185.9 秒，而墙钟过了 4.63 小时 —— **说明它在断网期间重启过**。
本次 79 秒的短窗口内没有出现这个现象（`seq` 连续递增）。
**重启原因未查明，记为待办。**

```bash
# 5) 恢复服务器，并确认没有补发
```
